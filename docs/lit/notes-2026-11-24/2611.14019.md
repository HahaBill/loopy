# 2611.14019: Program-Aided Patchable Skill Evolution (PASE)

arXiv 2611.14019v2, 11 Nov 2026, cs.CL, CC BY 4.0. 17 PDF pages (8 main, references, appendix A.1 to A.6). Jiahao Wang (1, equal), Yuqi Xiong (1, equal), Qing Yang (1), Zhipeng Xu (2), Zhenghao Liu (1, corresponding), Zulong Chen (2), Yubin Bao (1). 1 School of Computer Science and Engineering, Northeastern University, Shenyang. 2 Alibaba Group, Hangzhou. Code: github.com/NEUIR/PASE.

In one line: a skill-evolution loop where the same LLM reads its own trajectories and writes patches to a natural-language skill document and, optionally, a linked Python function. Patches are kept only if a held-out validation score goes up. Tested on spreadsheet tasks with three backbones. There is no separate teacher; the creator is the user model, except in a cross-model transfer table.

## Claim (key numbers and where they are)

1. PASE beats all baselines on average. Avg gain over the best baseline (EvoSkill) is +4.52 (Qwen3.6-27B, 62.79 vs 58.27), +3.31 (Qwen3.7-Plus, 66.26 vs 62.95), +2.77 (Gemma-4-31B, 59.14 vs 56.37) (Table 1). The abstract's "over 2.8%" is the smallest of these, rounded. I re-derived the Avg column: it is the mean of three benchmark means (SpreadsheetBench mean of Vrf, Soft, Hard; Domain-Spreadsheet Overall; TableQA mean of WikiTQ and HiTab). It matches to 0.01.
2. "Over 14%" in-domain gain (§5.1) holds only for Qwen3.6-27B on SpreadsheetBench-Verified: 82.98 vs EvoSkill 68.10 (+14.88). For Qwen3.7-Plus it is +7.74 (86.67 vs 78.93). For Gemma it is +2.38 (73.21 vs 70.83) (Table 1).
3. Program-only skills beat text-only skills on one model (Qwen3.6-27B): SpreadsheetBench 80.71 vs 78.93, Domain-Spreadsheet 50.17 vs 49.68, TableQA 72.61 vs 71.31, Avg 67.83 vs 66.64. Text plus program (PASE) is best at 69.28 (Table 2, §5.2).
4. Removing program evolution costs 4.74 Avg points (64.54 vs 69.28) (Table 2).
5. With programs, the validation curve peaks later (step 6 vs step 2) and swings less (Fig. 3a, §5.3).
6. Programs are touched by 62.2% of patches: 21.1% program only, 41.1% both, 37.8% text only (Fig. 3b).
7. Text skills get shorter: 1017.3 tokens for PASE vs 1393.7 EvoSkill, 2249.3 Trace2Skill, 2358 Human, 1981.3 LLM Skill (Fig. 3d). Program tokens are not counted.
8. PASE beats Trace2Skill in all 9 creator-user pairs by at least 3.07 Avg points (Fig. 4, Table 4).

## Method, in enough detail to reproduce

Representation (§3.1, Eq. 3). A skill set K = {(s_i, c_i)}. Each s_i is a Markdown skill (YAML frontmatter, "When to Apply", "Rules", and a "Program" section if a program exists). Each c_i is one Python function or empty. Skills are injected directly into the prompt (no retrieval; Limitations).

Inference agent (Eq. 4 and 5, Fig. 5). ReAct loop with a bash tool that runs Python (openpyxl, pandas) on an input xlsx and writes an output xlsx. The prompt slots are instruction, spreadsheet_path, answer_position, output_path, skill. Temperature 0.6, max context 131,072 tokens, max 30 ReAct iterations, no thinking mode set (A.3). Programs are called when the agent chooses to.

Evolution loop (§3.2, A.3). 10 evolution steps. Each step samples k = 8 training tasks with their trajectories, both successes and failures. A ReAct proposer (max 50 iterations) reads trajectories, current skills with programs, and past patches through four tools: read_trajectory(traj_id, steps), read_skill(skill_name), read_patch(patch_id), finish(). The first message lists the task input, number of trajectory steps, skill names, and ids, operations and targets of past patches (Fig. 6). The proposer model is not named; Fig. 4 calls it the "skill creator", so in the main table it is the same backbone as the user.

Patch format (Eq. 10, Fig. 6). p = (opt, target skill, edits to skill text, edits to program). opt is create, repair, or delete. Create gives full text and an optional program. Delete removes both. Repair gives line-level edits {line, operator +/-, content} for text and program separately; replace = delete then insert. Proposer rules: ground proposals in trajectory evidence, prefer patterns seen in several trajectories, keep skills concise, do not reference answer files, programs are optional, a program must be a parameterised reusable function.

Gate (Eq. 9). Apply the patch, score on a held-out validation set of 40 tasks, keep only if strictly better than the current set. Otherwise revert.

Data split (§4). SpreadsheetBench-Verified (400 tasks) split with seed 42 into 80 train, 40 validation, 280 test. Everything else is evaluation only.

Runs (A.3). Three independent evolution runs per method, test scores averaged. No variance is reported anywhere.

Baselines (§4, A.3). No Skill. Human Skill (Anthropic's official XLSX skill, not evolved). LLM Skill: one call with the prompt "You are an expert in spreadsheet manipulation. Write a skill guide (Markdown) for an AI agent that solves Excel/xlsx tasks using Python (openpyxl and pandas). Be specific and practical." Trace2Skill (parallel success and error analysts propose patches, hierarchical merge). EvoSkill (frontier search over SKILL.md candidates, validation-gated). Same backbone and inference prompt for all.

Ablations (Table 2, Qwen3.6-27B only). "w/ Text Skill" (all skills as text), "w/ Programmatic Skill" (all skills as programs), "w/o Program Evolution" (only text evolves), "w/o Adaptive Reading" (all trajectories, skills and patches put in context at once), "w/o Skill Updating" (neither text nor programs evolve). The paper does not say how "w/ Text Skill" differs from "w/o Program Evolution", or where the skills in "w/o Skill Updating" come from if nothing evolves.

## Setting, data, models

Benchmarks (A.2, Table 3). SpreadsheetBench: 912 tasks from Excel forums; Verified subset 400. Domain-Spreadsheet: 677 tasks in five domains, FIN 135, HR 185, RE 89, SAL 87, SC 181. WikiTableQuestions and HiTab: 1,000 sampled test questions each, tables converted to xlsx, answer written to cell A1.

Models (§4). Qwen3.6-27B and Gemma-4-31B-it (open, vLLM) and Qwen3.7-Plus (closed, Qwen API). Three models, all mid to strong. No small or weak model. Base strength by No Skill Avg: Qwen3.6-27B 32.04, Qwen3.7-Plus 45.15, Gemma-4-31B 48.87. On SpreadsheetBench-Verified alone the order is Qwen3.6-27B 43.81, Gemma 49.05, Qwen3.7-Plus 51.07.

## Metrics (exact definitions)

SpreadsheetBench: Verified accuracy (Vrf), Soft and Hard accuracy, following Trace2Skill. The paper does not define Soft and Hard itself. My understanding of SpreadsheetBench: Soft gives credit per test case, Hard requires all test cases. Not stated here. Domain-Spreadsheet: Pass@1 per domain under its official protocol; Overall is the size-weighted mean (I checked: Qwen3.6-27B No Skill gives 21.07). WikiTQ: denotation accuracy. HiTab: execution accuracy. Avg in Table 1: mean of the three benchmark means (see Claim 1). In Table 2 the columns are different: SpreadsheetBench is Vrf only and "TableQA" is HiTab only (Vanilla 42.63 = HiTab No Skill). Table 2 Avg is the plain mean of its three columns. So Table 1 and Table 2 Avg are not the same quantity.

## Results, including weak and negative ones

Table 1 per model, Avg: Qwen3.6-27B No 32.04, Human 48.97, LLM 46.16, Trace2Skill 57.03, EvoSkill 58.27, PASE 62.79. Qwen3.7-Plus No 45.15, Human 55.07, LLM 52.31, Trace2Skill 59.28, EvoSkill 62.95, PASE 66.26. Gemma No 48.87, Human 51.00, LLM 45.24, Trace2Skill 53.11, EvoSkill 56.37, PASE 59.14.

Places where PASE is not best (Table 1, bold marks in the PDF agree): Qwen3.6-27B SAL, Trace2Skill 40.61 vs 39.85. Qwen3.7-Plus WikiTQ, EvoSkill 86.54 vs 86.14. Gemma FIN, Human Skill 49.88 vs 49.63. Gemma WikiTQ, LLM Skill 84.36 vs 81.43. Gemma SAL ties EvoSkill (37.16). So "consistently outperforms all baselines" is true on Avg, not per column.

Harm below No Skill. PASE on Gemma WikiTQ: 81.43 vs No Skill 83.06 (-1.63). Gemma user with Qwen3.7-Plus-made PASE skills: WikiTQ 84.60 vs 83.06 (fine), but Qwen3.7-Plus user with Gemma-made skills: WikiTQ 83.57 vs 84.52 (-0.95) (Table 4). Text baselines hurt Gemma more often: LLM Skill Vrf 44.05 vs 49.05 (-5.00), Avg 45.24 vs 48.87 (-3.63); Human Skill HR 36.22 vs 42.34, RE 31.84 vs 39.33, WikiTQ 80.29 vs 83.06, HiTab 59.73 vs 63.01. Human Skill also hurts Qwen3.7-Plus HiTab (62.95 vs 65.92). The weakest model (Qwen3.6-27B) is never hurt by any skill on Avg.

Generic text skill by model strength. LLM Skill (generic, written from the task description, no trajectories) minus No Skill on Avg: Qwen3.6-27B +14.12, Qwen3.7-Plus +7.16, Gemma -3.63. Generic advice helps the weakest base and hurts the strongest base. The authors note only that LLM Skill "even underperforms" on Gemma (§5.1).

Program vs text by model strength (my computation). PASE minus EvoSkill on Avg: +4.52 (weakest, Qwen3.6-27B), +3.31 (Qwen3.7-Plus), +2.77 (strongest base, Gemma). This shrinks with base strength. PASE minus Trace2Skill: +5.76, +6.98, +6.03. No trend. In the cross-model grid (Fig. 4), PASE minus Trace2Skill averaged over creators, by user: Qwen3.6-27B 4.61, Qwen3.7-Plus 6.10, Gemma 5.10. No monotone trend. Three points, no CIs. I would not read an interaction from this.

Ablation (Table 2). All rows on one model. Program-only beats text-only by 1.19 Avg points. No CIs, no per-run spread, so this gap may be inside run-to-run noise. "w/o Skill Updating" (65.02) is still far above Vanilla (35.84) and above EvoSkill's Vrf in Table 1 (77.74 vs 68.10). That is odd if no evolution happens; the paper does not explain it.

Cross-model transfer (Table 4, A.4). Claims checked against the table:
- "Stronger users make better use of skills": Qwen3.7-Plus user averages 64.01 over creators vs Qwen3.6-27B 63.53 and Gemma 58.31. Holds weakly.
- "Gemma-made skills are executed better by the other two models, even outperforming their self-evolved skills": true for Qwen3.6-27B (63.74 vs 62.79), false for Qwen3.7-Plus (62.86 vs 66.26).
- "Qwen3.7-Plus skills reach 64.09 and 60.58 on Gemma and Qwen3.6-27B": the table says 60.62 (Gemma user) and 64.05 (Qwen3.6-27B user). Numbers swapped and slightly off in the text.
- Fig. 4 minimum gap 3.07 (Qwen3.7-Plus creator, Qwen3.6-27B user, 64.05 vs 60.98): checks out. 4.89 and 5.01 check out.

Evolution dynamics (Fig. 3a). Values are multiples of 2.5, which fits a 40-task validation set. Both curves start at 30. "w/ program" goes about 77.5, 80, 75, 82.5, 82.5, 87.5 (peak, step 6), 82.5, 77.5, 82.5, 80. "w/o program" goes about 75, 82.5 (peak, step 2), 77.5, 70, 80, 67.5, 75, 72.5, 65, 75. The peaks differ by 5 points, which is 2 of 40 tasks. One run, no error bars, model not named. With the strict gate the kept skill set should never drop on validation, so these curves must be candidate scores, not kept scores. The paper does not say.

## Limitations

Theirs: no skill retrieval (all skills injected); the agent can bypass programs and rewrite the logic in bash, and they have no way to force program use; the strict gate rejects neutral patches that might help later.

Mine:
- No CIs, no seed spread, despite three runs. Most gaps between PASE and EvoSkill are 2 to 5 points on test sets of 280 to 1,000; unknown if significant.
- Program call rate is never measured. We cannot tell how often the gain comes from the agent calling the program vs reading the shorter text.
- The proposer model is not named. If it is the backbone, the three models differ as proposers and as users at once.
- Possible train-test overlap: evolution trains on 80 Verified tasks, and Soft and Hard are reported on "the full benchmark (912)" (A.2). If Verified is a subset of the 912, train and validation tasks are inside the Soft and Hard test numbers. Not addressed.
- Table 2 rows are underspecified (Text Skill vs w/o Program Evolution; what w/o Skill Updating evaluates).
- Table 1 and Table 2 define Avg and TableQA differently.
- Fig. 3a is one run on 40 validation tasks; a 5-point peak gap is 2 tasks.
- Some text claims do not match the tables (A.4 numbers swapped; Gemma-skill claim half false; "consistently outperforms" fails on 4 cells).
- Only spreadsheet-style tasks. One domain family.

## Untested assumptions

- That separating procedural logic into code is what drives the gain, rather than the different proposer prompt, adaptive reading, or line-level patching. The text-only arm uses the same pipeline in Table 2, but only on one model and without variance.
- That the agent actually executes the program when it is present.
- That shorter text skills mean less context; program tokens are not counted.
- That validation gains on 40 tasks transfer; no test of gate noise.
- That stronger users exploit programs better; inferred from three points.

## Overlap with Loopy (K1 to K6)

- K1 (same failure, same teacher, same student, text vs code head to head): partly. Table 2 compares text-only, program-only and both, built by the same pipeline, used by the same model (Qwen3.6-27B). But the "teacher" is the student itself, the artifacts are global skills distilled from 80 tasks, not per-failure, and there is one model and no variance. Fig. 4 has creator not equal to user (teacher-like), but compares two different algorithms (Trace2Skill text vs PASE text plus code), not two forms of the same knowledge.
- K2 (student-capability axis, form by strength interaction): partly. Three backbones and a 3x3 creator-user grid. But the form contrast (text-only vs program) exists only on one model (Table 2). Across models only method contrasts exist. PASE's edge over EvoSkill shrinks with base strength (+4.52, +3.31, +2.77) but its edge over Trace2Skill does not (Table 1). No weak or small model. No crossover shown for code.
- K3 (task difficulty axis): not covered. No difficulty split. Hard vs Soft is a scoring strictness, not task difficulty (PASE minus EvoSkill is larger on Hard than Soft for all three models, e.g. +6.28 vs +3.92 on Qwen3.6-27B, but this is not a difficulty analysis).
- K4 (harm to capable students): partly, weak. PASE falls below No Skill on WikiTQ for Gemma (-1.63) and in one transfer cell (-0.95), the near-ceiling benchmark. Text baselines hurt the strongest-base model (Gemma) on several columns. No per-task broke-what-passed-alone counts.
- K5 (controls): partly. LLM Skill is close to a generic note: +14.12 Avg on the weakest model, -3.63 on the strongest base. That is our generic-note control in spirit. The keep rule is a held-out validation gate (40 tasks), not "the student re-passes the task the artifact came from". No repeating-task variants; SpreadsheetBench tasks are diverse.
- K6 (cost and break-even, counting failed builds): not covered. No token or dollar cost, no count of rejected patches as wasted builds, no break-even.

Plain answers:
- Does it compare a natural-language form with a program form of the same knowledge on the same models? Only in Table 2, on one model (Qwen3.6-27B), same pipeline. Program-only 67.83 vs text-only 66.64 Avg.
- Across how many models and what strength? Three: Qwen3.6-27B, Qwen3.7-Plus, Gemma-4-31B. All mid to strong. No small model.
- Does more code help weak models more than strong ones, or hurt strong ones? Weak, mixed signal. PASE over EvoSkill: +4.52 weakest, +2.77 strongest base. PASE over Trace2Skill: no trend. PASE hurts the strongest-base model only on one near-ceiling column (Gemma WikiTQ -1.63). Generic text skill shows a clearer pattern: +14.12 weakest, -3.63 strongest.
- Any analysis by task difficulty? No.

## What we can no longer claim

- That no one has compared text skills with executable program skills distilled from agent trajectories. PASE does (Table 2), and finds program-only slightly ahead and text plus program best.
- That no one has shown code artifacts transfer across models. PASE claims transfer of text plus program skills across 3x3 creator-user pairs (Fig. 4).
- That a generic LLM-written skill hurting a stronger model is new. Table 1 shows it on Gemma (Avg -3.63), though the paper does not frame it.

## What stays open

- Per-failure artifacts from a stronger teacher, text note vs function, on the same failure, with a re-run pass gate.
- A real student-strength axis with weak students, and a form by strength interaction or crossover with CIs.
- Per-task harm counts: how many tasks a capable student passed alone and fails with the program.
- A placebo or generic note control matched in length to the tailored note.
- Task difficulty split.
- Build cost, failed builds, and break-even over repeated uses.
- Whether the student actually calls the function (call-rate logging).
- AppWorld or any API-calling multi-app setting.
