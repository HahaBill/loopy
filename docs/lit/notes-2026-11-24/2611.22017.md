# 2611.22017v2: SkillBuffBench

arXiv 2611.22017, version v2, dated 23 Nov 2026 (cs.AI). License: arXiv perpetual non-exclusive.

Authors: Gengyue Dong (Dept. of Engineering Science, Oxford), Ye Wei (MRC Weatherall Institute of Molecular Medicine, Oxford), Zheng Zhu and Yidong Han (Dept. of Materials, Imperial College London), Jiale Miao (Dept. of Mathematics, UCL), Guanghui Li (BraneMatrix AI, Shanghai; corresponding author). First five are equal contribution.

## Bottom line for Loopy

This is a protocol paper with **no results**. The abstract and the "Status of this version" paragraph (Sec. 1) say the runs are in progress and results will be added later. It cannot support or refute any Loopy claim with data. It covers none of K1 to K6 with evidence. Its only value to us is design ideas (normalised gain, pass^k vs pass@k, cost per successful run, invocation logging) and one cited number from SkillsBench.

## Claim

- The design claim: Skill gains in prior work come from a hand-picked Skill and a blank-slate agent. Deployment has neither. So they add a third Skill condition (automatic invocation from an installed library) and a memory factor (off/on), crossed with 4 harnesses and n=11 models (Sec. 1, Sec. 2.1, Table 1, Fig. 1).
- The only empirical number in the paper is cited, not measured: SkillsBench [19, arXiv 2602.12670] found curated Skills raise mean score by 16.6 points across 87 tasks and 18 model-harness configurations, gain varies by domain and harness, 13 tasks get worse with Skills, and self-written Skills did not substitute for curated ones (Sec. 1, page 2).

## Method (enough to reproduce the design)

- Factorial design (Sec. 2.1, Table 1): harness (4: Ginkley by BraneMatrix, Codex, Claude Code, OpenCode) x model (n=11, one shared pool, every model under every harness) x Skill condition (3) x memory mode (2) x 4 tasks x 3 repeats.
- Per model: 4 x 3 x 2 x 4 x 3 = 288 runs; 144 under memory off. Whole experiment with n=11: 3168 runs, 1584 under M0 (Sec. 2.8).
- Skill conditions (Sec. 2.3):
  - Empty set: no Skill installed. Baseline.
  - S, curated: the most relevant Skills, chosen by a person, are available.
  - A, automatic: a Skill library is installed and the harness's own mechanism decides what gets loaded.
  - S minus empty bounds what Skills can add. A minus S is "lost to discovery". The prompt never names a Skill.
- Skill format (Sec. 2.2): a directory with SKILL.md (name + short description). Harness puts only names and descriptions in context. The model decides from the descriptions whether to load the body. Bundled scripts and reference files are read as needed.
- Leakage rule (Sec. 2.3), copied from SkillsBench: a Skill must serve a class of problems. No task outputs, task-specific paths or constants, or commands that solve one instance directly.
- Skill text is **not disclosed** (Sec. 2.3, "What is disclosed about Skills"). Skills are the property of contributors. Only their purpose is described. Instructions, scripts, templates and reference material are not reproduced.
- Memory (Sec. 2.4): M0 = new session, new working directory, new memory namespace each run, with a 5-rule isolation procedure. M1 = "the agent may use memory of successful task completions accumulated under the same experimental definition." Headline results use M0. How M1 memory is built, ordered or filtered is not specified.
- Harness memory files: CLAUDE.md (Claude Code), AGENTS.md (Codex, OpenCode); Claude Code also keeps self-written notes (Sec. 2.2).
- Toolsets belong to tasks (Sec. 2.5): each task declares tools and pinned versions. A tool only one harness has is disabled.
- Network (Sec. 2.5): sandbox allows outbound only to the model API plus services a task declares (for example a crystal-structure database). A run that tries to reach a blocked source is flagged and not counted.
- Controlled variables (Sec. 2.7): temperature 0, top-p 1, fixed seed where the provider exposes them; same output-token limit and same budgets on rounds, wall-clock and tokens across conditions; fixed task order; hashes of harness, toolset, inputs, verifier recorded.
- Infrastructure failures (Sec. 2.8): re-run or flagged, never charged to the model. Recurring failures make a cell "not comparable".
- Failure taxonomy (Sec. 2.10, Table 4): one primary type per failed run, diagnostic only.

## Setting, data, models

- Tasks (Sec. 3, Table 5): 4 expert-contributed research tasks in 2 domains.
  1. Oxygen tracer diffusion from SIMS (fit D* and k*, judge trust).
  2. XRD phase identification and Le Bail unit-cell refinement (GSAS-II, crystal-structure database).
  3. Regulatory target prioritisation: rank enhancer-gene pairs from a public CRISPR study (Fulco et al. 2019), outcomes withheld.
  4. Spheroid structure from 3D microscopy: envelope, nuclei, radial density, neighbour distances.
- Each task ships with the Skill its expert uses. XRD has two Skills.
- Model pool (Table 2): Claude Fable 5.2, Claude Opus 5.5, Gemini 4 Argon, Gemini 3.8 Flash, GPT-6 Astra, GPT-6.1 Sol, DeepSeek-V4-Pro, Qwen3.8, Kimi K3.1 Pro, GLM-5.3, MiniMax-M3. All are frontier or near-frontier. There is no weak model in the pool.

## Metrics (exact definitions, Sec. 2.9)

- Per-run score y_ir in [0,1] from a deterministic verifier; pass b_ir = 1[y_ir >= tau_i], tau_i set by the contributor before any run.
- Task score p_i = mean over R=3 repeats. Cell score P = unweighted mean over N=4 tasks (Eq. 1).
- Absolute gain Delta_c = P_c - P_empty; normalised gain g_c = (P_c - P_empty) / (1 - P_empty) (Hake 1998), for c in {S, A} (Eq. 2). Memory effect = M1 minus M0 at fixed Skill condition.
- Uncertainty: nonparametric bootstrap over tasks, B=10,000, same resampled indices for every condition, 95% percentile interval (Eq. 3).
- Reliability with k=R=3: pass^k = fraction of tasks passed on all k runs; pass@k = fraction passed at least once (Eq. 4).
- Efficiency: mean cost, tokens, rounds, wall-clock per run; plots of each against P; cost per successful run = total cell cost / number of passing runs (charges failed attempts).
- XRD score (Sec. 3.1.2): s_R = max(0, 1 - Rwp/20%), s_chi = min(chi^2, 1/chi^2), s_cell linear to 0 at tolerance; y = G (0.25 s_R + 0.25 s_chi + 0.5 s_cell), G = 1 only if phase matches and artifacts exist.
- SIMS score (Sec. 3.1.1): per-point residuals, normalised RMS, CI coverage of D* and k*, joint confidence region over (log D*, log k*). Combination weights are not given.
- Regulatory task: average precision with coverage. Spheroid: overlap, surface distance, volume error, one-to-one nuclear matching; outright fail for an unsupported 3D claim or calling a detected count a cell count. Score combination rules for SIMS, regulatory and spheroid are not stated.

## Results

None. No numbers for any condition, model, harness or task. No weak or negative results to report. The paper promises per-task results "so that tasks on which Skills hurt are visible" (Sec. 2.11), but none are present.

## Limitations

Theirs: results not yet in; the suite is small and will grow; Skill text withheld.

Mine:
- No data at all. Nothing to cite as evidence.
- N=4 tasks. A bootstrap over 4 tasks has very few distinct resamples (35 multisets), so the 95% intervals will be coarse and close to the min/max of task scores.
- 3 repeats at temperature 0 test little run-to-run variance where providers honour temperature 0.
- Skills undisclosed, so nobody can check what the curated condition contains or whether scripts do the work.
- Conflict of interest: Ginkley is the corresponding author's company's harness.
- The model pool is frontier only. It cannot test whether weak models gain more or less.
- M1 memory is described in one sentence. It is not reproducible from the text.
- Score aggregation rules for 3 of 4 tasks are not given.

## Untested assumptions

- That a Skill's value separates cleanly into content (S) and discovery (A minus S).
- That temperature 0 plus a fixed seed makes repeats exchangeable across all 4 harnesses and 11 providers.
- That one expert's Skill is a fair "curated" upper bound for each task.
- That mapping all harnesses to one task-declared toolset is neutral across harnesses.

## Overlap with Loopy

- K1 (text vs executable, same failure, same teacher, same student): **not covered**. Skills may bundle scripts (Sec. 2.2), but text and scripts are never separated, there is no teacher, and Skills are not built from failures.
- K2 (student-capability axis with form x strength interaction): **not covered**. 11 models, but all strong, no results, and Skill form is not varied.
- K3 (task difficulty, text fading while code holds): **not covered**. Per-task and per-domain breakdowns are planned only.
- K4 (non-text help hurting capable students): **not covered**. Only the cited SkillsBench fact that 13 of 87 tasks got worse with Skills.
- K5 (placebo note, keep-only-if-re-run-passes, variants of a repeating task): **not covered**. No placebo condition. Repeats are the same task, not variants. M1 memory of successful completions is the nearest idea but is unspecified and unmeasured.
- K6 (cost and break-even with failed builds): **partly, design only**. "Cost per successful run" charges failed attempts to successes (Sec. 2.9). There is no cost of building the Skill, no repeated-use amortisation and no break-even.

Plain answers:
- Gain vs model strength: unknown. No per-model numbers exist in this version.
- Do Skills include scripts? Yes, optionally (Sec. 2.2). The text part and the executable part are not separated anywhere.
- Any case where a Skill hurts a strong or weak model? Not measured here. Cited: SkillsBench, 13 tasks worse with Skills.
- Analysis by task difficulty? None.

## What we can no longer claim

Nothing in Loopy's core claims is pre-empted by this paper. We should not claim to be first to report pass^k vs pass@k or cost per successful run for skills; this paper defines both for the skill setting.

## What stays open

All of K1 to K6. Follow-up lead: SkillsBench (arXiv 2602.12670) has the actual harm data (13 worse tasks, self-generated Skills fail) and should be read in full before we cite "skills can hurt".
