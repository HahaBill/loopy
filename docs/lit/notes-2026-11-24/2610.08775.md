# 2610.08775: Agent in a Bottle: Can LLM Agents Turn Their Capabilities Into Cheap, Scalable Artifacts?

arXiv 2610.08775v1, 6 Oct 2026, cs.AI. About 22 pages (10 main, references, appendix A to E). Ankit Sonthalia (1), Haritz Puerto (2), Alexander Rubinstein (1), Martin Gubri (3), Seong Joon Oh (4). 1 University of Tübingen. 2 ELLIS Institute Tübingen, Max Planck Institute for Intelligent Systems, Tübingen AI Center. 3 École Polytechnique, Institut Polytechnique de Paris, CNRS. 4 KAIST AI. Code: github.com/aktsonthalia/bottled (MIT).

In one line: a benchmark (BOTTLED) where an LLM agent gets a whole unlabelled workload of millions of instances of one narrow task, plus a 5M-token and 10-hour budget, and must build any cheap artifact (program, fine-tuned small model, hybrid) that answers all of it. There is no student. The artifact replaces the model. Artifact form is free and is not analysed.

## Claim (key numbers and where they are)

1. Zero-shot skill does not predict bottling skill. On MAVE, GPT 5.6 Terra and Sonnet 5 both score about 0.44 zero-shot F1, but bottle to 0.405 and 0.154 (§1, §4.1, Fig. 2, Table 1).
2. Bottling usually loses quality: 48 of 60 runs fall below their own model's zero-shot 95% CI; 40 of 60 fall below even the worst model's zero-shot CI (Abstract, §4.1, Fig. 2).
3. A naive distillation script often wins: 31 of 60 runs score below the better of two fine-tuned small students given the same 5M tokens; 21 of 60 below both (Abstract, §4.1, Fig. 2).
4. Bottling can be very cheap: Opus 5 on ESCI keeps about 82% of zero-shot macro-F1 (0.499 vs 0.609) at about 657 times lower cost ($26.28 vs an estimated $17,273) (Abstract, §1). Opus 5 on MAVE keeps over 95% (0.461 vs 0.483) at about 889 times lower cost ($31.40 vs $27,914) (§4.1).
5. Price does not buy bottling skill: GLM 5.3 Flash gets aggregate relative gain 0.387 for $0.81; Opus 5 gets 0.421 for $29.02; GPT 5.6 Sol gets 0.061 for $11.73 (Table 1, Fig. 1 right).
6. Bottling is competitive with Jev, a cheap "system one" model: Opus 5 bottled ESCI reaches 94% of Jev's 0.531 at 25% of Jev's projected cost; Gemini 3.1 Pro bottled RAID reaches 97% of Jev's 0.846 AUROC at about 2% of cost (§4.2, Fig. 3).
7. Budget limits explain some but not most of the gap: after rerunning the 21 budget-terminated runs without a hard stop, 47 of 60 runs are still below zero-shot CI (§4.3, Fig. 4).

I re-derived: 17,273 / 26.28 = 657; 0.499 / 0.609 = 82%; 27,914 / 31.40 = 889; 0.461 / 0.483 = 95.4%; 0.497 / 0.593 = 84%; 0.265 / 0.573 = 46%; 26.28 / 104.89 = 25%; 4.69 / 223.16 = 2.1%. All match.

## Method, in enough detail to reproduce

Problem (§3.1). A narrow task has one fixed instruction d for every instance. A workload is N unlabelled instances (2.6M to 5.6M here). Quality is a workload-level score s(y_hat, y).

Cost of one call (Eq. 1): c = t_in + 0.1 t_cache + 2 t_out (weighted tokens).

Zero-shot baseline (Eq. 2, §3.5.1). Prompt M with d and one instance, no tools. Cost extrapolated from a uniform sample of n = 1000 instances; the same 1000 for every model. Unparseable answers get the fallback.

Bottling (Eq. 3 to 5). The same model M runs as an agent in the OpenCode harness with a shell, Python, one A100 40GB, 8 CPU cores, 64GB RAM, internet through a logging proxy, and API access to M only (no other model). It gets d and the whole workload as one file. It must write out.txt with one prediction per line. Artifact phi is unconstrained: rule program, fine-tuned SLM, retrieval index, or hybrid routing hard cases back to M. Cost C_bot = C_build (all tokens spent exploring, labelling, training, validating) + sum over instances of c_exec (tokens phi spends on M at inference). Footnote 2: c_exec is almost always zero because agents build self-contained artifacts. Objective: maximise s subject to C_bot <= 5M weighted tokens and time <= 10 hours, with no labels.

Budget tools. MCP tools get_api_budget_mtok and get_time_budget_min. The harness stops when a budget is exhausted. mark_task_complete ends the run voluntarily (App. C).

Leakage control (§3.3, App. D). Proxy blocks URLs for the datasets and models trained on them. An agentic judge (GLM 5.3 Flash in OpenCode) audits each run's trace, proxy logs and workspace and returns CLEAN, CONTAMINATED or NEEDS REVIEW. 59 of 60 CLEAN; one GLM 5.3 Flash RAID run used a ModernBERT detector trained partly on RAID (AUROC 0.857) and was replaced by a rerun with an updated blocklist. All 21 ablation reruns judged CLEAN.

Scoring (§3.4). Missing predictions get a no-information fallback: empty string (MAVE), uniform random label (ESCI), 0.5 (RAID). Relative gain r = (s - b) / (a - b), where b = score of all-fallback answers and a = gold scored against itself. R(M) = mean of r over the 3 tasks (Eq. 6). Bottled R uses 6 runs per model (3 tasks by 2 runs).

SLM distillation baseline (§3.5.2, App. B). GLM 5.3 Flash labels uniformly sampled instances zero-shot until 5M tokens are spent: 12,765 (MAVE), 9,412 (ESCI), 6,567 (RAID) labels. 10% held out; best held-out-loss epoch kept. Qwen3-0.6B: 3 epochs, AdamW, lr 1e-5, batch 64, 10% warmup, cosine; inference temp 0.7, top-p 0.8, top-k 20. SmolLM2-360M-Instruct: 2 epochs, AdamW, lr 1e-3, batch 128, 10% warmup, cosine; inference temp 0.2, top-p 0.9. Three runs each, thinking off. No tuning on purpose.

Jev (§4.2, App. E). Jev 1.13.0 via TypeSafe AI's system_one endpoint, one call per instance on the same 1000 samples. ESCI uses the "choice" question type, RAID the "noul" type. Cost $0.042 per million input tokens, output unmetered. Cannot do MAVE (no free text).

Over-budget ablation (§4.3). The 21 runs stopped by budget are rerun under identical settings, budgets still stated, hard stop disabled. Reruns replace originals for the recomputed means.

## Setting, data, models

Tasks (§3.2).
- MAVE: about 4.77M Amazon product-attribute pairs; return the attribute value exactly as written, or a NO_VALUE token (about 1.78M pairs have none). F1 over all predictions.
- ESCI: about 2.62M query-product pairs; label Exact, Substitute, Complement or Irrelevant. Macro-F1 (class-imbalanced).
- RAID: about 5.62M documents, human or machine written, with adversarial attacks; output confidence of machine authorship. AUROC.

Models (Table A1, via OpenRouter, prices as of September 2026): Qwen 3.8 Flash, Qwen 3.8 Max, Sonnet 5, Opus 5, Gemini 3.1 Flash-Lite, Gemini 3.1 Pro, GPT 5.6 Terra, GPT 5.6 Sol, GLM 5.3 Flash, GLM 5.3. Ten models, 3 tasks, 2 bottling runs each = 60 runs.

## Metrics (exact definitions)

- Native: F1 (MAVE), macro-F1 (ESCI), AUROC (RAID), on the full workload for bottling and on the 1000-sample for zero-shot and Jev.
- Zero-shot 95% CI: bootstrap, 2000 resamples of the 1000 instances (§4).
- Relative gain r and aggregate R(M): Eq. 6 above.
- Cost: weighted tokens (Eq. 1) converted to USD at Table A1 prices. Zero-shot and Jev full-workload costs are projected from the 1000-sample. GPU and CPU time are not costed.

Positive.
- 6 of 60 runs recover at least 95% of zero-shot (§4.1).
- Opus 5 tops aggregate at 0.421; GLM 5.3 Flash and Gemini 3.1 Pro about 0.39 (§4.1).
- After the over-budget rerun, Opus 5 RAID goes 0.713 to 0.929 AUROC, above its zero-shot. GPT 5.6 Sol MAVE more than doubles to 0.386 (90% of zero-shot); Sol RAID reaches 0.800 (about 86%) (§4.3, Fig. 4).

Negative.
- Even the best bottlers lose over a quarter of zero-shot quality on average; the worst lose about 90% (§4.1). Opus 5, GLM 5.3 Flash, Gemini 3.1 Pro zero-shot aggregate about 61%, 54%, 59% vs bottled 42%, 39%, 39%.
- Bottled score ranges are more than 5x, 3x and 2x the zero-shot ranges on MAVE, ESCI, RAID (§4.1).
- 21 of 60 runs hit the token budget; 8 of these delivered no out.txt. GPT 5.6 Sol caused 4 of the 8 (§4.1). One Sol run launched sequential API labelling of thousands of samples and ran out.
- 39 of 60 runs stopped voluntarily, some with bad solutions. A Gemini 3.1 Flash-Lite ESCI run read a truncated file preview, concluded there were 49 instances, wrote 49 answers and stopped with about 4.95M tokens unused (§4.3).
- Sonnet 5 on MAVE, both runs, just prompted off-the-shelf Qwen2.5-1.5B-Instruct over the workload with no fine-tuning: F1 0.194 and 0.113 vs its zero-shot 0.444, after spending 4.68M and 1.00M tokens (§4.3).
- GPT 5.6 Sol ESCI gains only 0.074 when allowed over budget and stays at about 49% of zero-shot (§4.3).
- GLM 5.3's RAID bottled AUROC is 0.516, near chance, though its MAVE and ESCI are strong. Not discussed.

## Limitations

Theirs. Few explicit ones. They note cost conclusions depend on provider pricing (§4.1), that the blocklist may miss leakage (§3.3), and that the instruction text differs between zero-shot and bottled modes (footnote 1).

Mine.
- Two runs per model and task. Run spread in Fig. 2 is large, so model rankings are fragile.
- Artifact type is never tabulated. We do not learn how many runs built a program vs a fine-tuned model vs a hybrid, or which form scored best. Only anecdotes (Sonnet's unfine-tuned SLM, GLM's downloaded detector, Sol's API labelling).
- Cost counts only API tokens. Ten hours of A100 time is free in the accounting. That flatters bottling against zero-shot and Jev.
- Zero-shot quality is measured on 1000 instances; bottled quality on millions. The CI covers sampling but not any shift in distribution.
- Zero-shot runs are non-agentic with no reasoning budget stated; bottling agents can set reasoning_effort. The comparison mixes mode and compute.
- Three tasks, all classification or extraction over text. No multi-step or tool-using tasks.
- Contamination audit uses GLM 5.3 Flash, one of the evaluated models, as judge.
- No per-instance analysis, so we cannot see which instances the artifact breaks that the model alone gets right.

## Untested assumptions

- That one fixed harness (OpenCode) separates model skill from harness skill. Only one harness is run.
- That restricting each agent to its own API is fair. A weak model cannot ask a stronger one for labels, which is exactly the teacher setting Loopy uses.
- That the workload is i.i.d. enough that a sample-trained artifact generalises. No distribution shift test.
- That the fallback answer is uninformative for ESCI (uniform random label under class imbalance gives a nonzero macro-F1 baseline, which r subtracts, so this is handled, but the choice is not discussed).
- That more budget would help. The ablation shows it helps some models only.

## Overlap with Loopy (K1 to K6)

What exactly is the artifact? Anything executable that maps an input to an answer: a rule program, a fine-tuned small model, a retrieval index, or a hybrid. In practice, self-contained (c_exec about zero). It is not advice and it is not read by a student. It replaces the model.
Does it compare artifact forms on the same students? No. Form is the agent's choice and is not broken down. There are no students in the Loopy sense; the only "students" are the two SLM baselines, which are a fixed distillation recipe, not a form chosen per failure.
Across how many models and of what strength? Ten builder models from cheap (Gemini 3.1 Flash-Lite, Qwen 3.8 Flash, GLM 5.3 Flash) to frontier (Opus 5, GPT 5.6 Sol, Gemini 3.1 Pro). Strength here is the builder's, not a consumer's.
Does any form help weak models more, or the reverse? Not measured. The nearest finding is the reverse direction of Loopy's question: builder price or zero-shot skill does not predict artifact quality (GLM 5.3 Flash near Opus 5; Sonnet 5 and GPT 5.6 Sol poor).
Any case where an artifact hurts? Yes in the sense that 48 of 60 artifacts score below their own model's zero-shot. The artifact is worse than the model answering each instance itself, traded for 2 to 3 orders of magnitude in cost. No per-instance "passed alone, broken by artifact" count.

- K1 (text vs code, same failure, same teacher, same student): NOT covered. No text form, no student, no per-failure artifacts.
- K2 (student-capability axis, form by strength interaction): NOT covered. There is a capability axis over 10 builders, but no consumer student and no form comparison. Useful side fact: builder strength does not predict artifact quality (Fig. 1, Table 1).
- K3 (difficulty axis): NOT covered. Three tasks, no difficulty split.
- K4 (harm from executable help to capable models): PARTLY, as an analog only. Executable artifacts built by capable models usually score below those models alone (48 of 60 below zero-shot CI). But this is replacement, not help to a student, and there is no per-instance flip count.
- K5 (controls): PARTLY. The workload is a genuinely repeating task (one fixed question, millions of instances). There is a placebo-like floor (all-fallback answers) and a naive distillation baseline, but no generic-note control and no "keep only if a re-run passes" gate; agents have no labels to check against.
- K6 (cost and break-even with failed builds): PARTLY, the strongest overlap. Cost is split into C_build plus N times c_exec (Eq. 4), every exploration token counts against the build, and the 8 runs that built nothing are scored with fallbacks rather than dropped. But there is no break-even curve against N, failed build attempts inside a run are not counted separately, and GPU time is free.

## What we can no longer claim

- That letting an LLM build an executable artifact to amortise a repeating task, with cost split into build plus per-use, is a new framing. Eq. 4 is that framing.
- That a capable model will build a good executable artifact. Many do not, and zero-shot skill does not predict it.
- That executable artifacts can match the model's own quality at a tiny fraction of the cost in general. It happens in 6 of 60 runs here.
- That a cheap model cannot build a competitive artifact. GLM 5.3 Flash does for under $1.

## What stays open

- Everything about artifacts that help a separate, weaker student rather than replace the model.
- Text note vs executable function from the same failure, same teacher, same student (K1).
- Whether the best form depends on student strength (K2).
- Text fading with difficulty while code holds (K3).
- Per-instance harm: tasks the student passed alone that the artifact breaks (K4).
- A student re-run gate and a generic placebo note (K5).
- Break-even over repeated uses that counts failed builds explicitly (K6, partly).
- Agentic, multi-turn API tasks like AppWorld. All three BOTTLED tasks are single-input text labelling.

Leads this paper leans on, worth reading for Loopy: Huang et al. 2026, arXiv 2608.11338, "Better, Faster, Stronger: Programmatic Skill Learning Best Reduces Agent Cost" (abstract claims skills-as-programs give the best cost reduction among skill learning methods; likely closest to K1 and K6). Wang et al. 2025a, arXiv 2504.06821, "Inducing programmatic skills for agentic tasks" (ASI). Wang et al. 2025b, Agent Workflow Memory (text workflows). This paper groups these as "partial forms of bottling" in §2 and does not compare them.
