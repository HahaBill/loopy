# PLVR: Program Learning with Verifiable Rewards: Distilling Expert Traces into Programs

- arXiv: 2610.19148v3, 12 Nov 2026, cs.AI. License CC BY 4.0.
- Authors: Vishvesh Bhat (CoreThink AI), Muhammad Ahmed Mohsin, Asad Aali (Stanford).
- Read on 2026-11-20 from the arXiv HTML full text plus the PDF (30 pages).
- Code and data: not released. "Will be released following peer review" (Reproducibility Statement).

## Claim (key number and where it is)

A program built once from a teacher's traces lets a frozen 8B model do procedural tool-use almost as well as larger frozen models.
Key number: on tau2-Bench Telecom, Granite-4.2-8B goes from 43.0% to 91.2% under the program. Three Nemotron students reach 93.3 to 94.4%. No other arm on any student passes 57.9% (Table 2, Section 5.1, Figure 2).
The claim is strong on Telecom only. On tau2 Retail and LiveMCPBench the authors say the program is "competitive with the best baseline", not better (Section 5.4).
The paper frames this as an estimate of "how much of the gap between base models is procedure" (Section 1, Section 6). The authors call it an upper bound.

## Method (enough to reproduce)

1. Training tasks. Claude 5 Opus writes 553 synthetic tasks in the benchmark formats: 142 retail, 178 telecom, 233 tool-search (Table 1). It uses the real tau2 tools, environment and policies. Split 80/20 train and held-aside validation. Five overlap guards: no benchmark ids, no shared customers, orders or fault sets, no near-duplicate text, validation kept out of fitting, no always-pass or unsolvable tasks (Section 3.1).
2. Teacher traces. Kimi-K3 runs every task with a generic prompt. Only traces that reach ground truth are kept: 539 of 553 (retail 128 of 142, the other two all kept).
3. Segments and clusters. No LLM here. Each assistant message is cut into segments typed reason, call, message or question. 3,141 segments. Embedded with text-embedding-3-small (1,536-d). k-means inside each type gives 35 clusters: 15 reason, 8 call, 9 message, 3 question (Section 3.2, Appendix E.1).
4. Primitives. Claude 5 Opus reads the clusters and writes 37 primitives in six groups (understand message 7, find tools 5, build call 8, check policy 7, troubleshooting conditions 6, finishing 4). Each primitive is ONE call to frozen Granite-4.2-8B with its own prompt, typed inputs, a JSON output schema, a deterministic verifier and a fallback value. The verifier rejects bad schema, quotes not found verbatim, facts that do not exist, expressions that do not evaluate (Section 3.2).
5. Rule library. Claude Sonnet 4.5 mines 125 executable rule codeblocks from the traces: 61 from tool-search, 64 from telecom. Retail has no library of its own (Section 3.4, Appendix F). Cost: 16 calls, about 287k prompt and 47k completion tokens.
6. Objective. "Process distance" d against the teacher's state-changing actions. 1.0 per missing or wrong-argument action, 0.5 per out-of-order action, 0.5 per extra state change, 1.0 for abnormal end, divided by number of expert actions, plus end-state checks. No LLM judge (Section 3.3).
7. Search. A* from a hand-written seed program (three blocks, one per task type). Edits: insert, remove or move a primitive or rule, or change flags. Only type-checked edits. Score f = |P| + 100 d, where |P| is rules switched on. Up to K=6 candidates per round, two runs each. Stop after three rounds with no gain. Final pick by pass rate on the synthetic validation split. Search student is Nemotron 3.5 Lightning. Programs scored: telecom 32, retail 87, tool-search 9 (Tables 4, 5).
8. Two forms at inference. For telecom and tool search the program RUNS and writes the chain of thought the student then acts on ("the program replaces the student's reasoning"). For retail the program is a GUARD: the student proposes an action, the program checks it against records, rules and consent, repairs it or sends it back (Section 1, Appendix B).

Not reproducible today: the primitives, rules, seed code and final code are only summarized in English (Appendices B, E, F). The seed is hand-written by the authors.

## Setting, benchmarks, models

- Benchmarks: tau2-Bench Retail (114 test tasks), tau2-Bench Telecom (114), LiveMCPBench (95). Multi-turn dialogue with a simulated user for tau2. Tool search over a large MCP registry for LiveMCPBench.
- Teacher (traces): Kimi-K3. Its accuracy on the test sets is never reported.
- Task writer and primitive author: Claude 5 Opus. Rule miner: Claude Sonnet 4.5. GEPA reflection model: gpt-4.1.
- Primitive executor: Granite-4.2-8B (8B), frozen.
- Students: Nemotron 3 Nano (30B, 3B active), Nemotron 3.5 Lightning (30B, 3B active), Nemotron 3 Super (120B, 12B active), and Granite-4.2-8B itself (Table 9, Appendix C).
- No weights change in the program arm.

## Metric

Accuracy (%) = pass@1 per run under each benchmark's own evaluator. One run per cell, except the Nemotron program cells on Telecom (mean of 3 runs). Averages are plain means of the three suite cells (Table 2 caption, Section 4.4).
Secondary: "spread" = max minus min accuracy across the three Nemotron students (Figure 3a). Tokens per task and FLOPs (2 x active params x tokens for inference).

## Baselines (exactly)

All given to the same students, all using the same kept traces or training split:
1. Vanilla: the student with chain-of-thought prompting.
2. SFT: LoRA fine-tune on the teacher traces. Process, outcome and process+outcome variants. 24 runs per student, one selected (Appendix D).
3. GEPA: the student's own SYSTEM PROMPT is optimized (10 iterations, minibatch 16, reflection by gpt-4.1, reward = exact call-set match, outcome only). Then the student runs as a plain tool-calling agent. This is the only text-form transfer arm (Appendix I).
4. ReAct planner loop, token-matched: Granite-4.2-8B writes a plan each turn, the student acts from that plan placed in its reasoning slot, Granite critics (policy, grounding) review, up to 2 revisions. 450,000 Granite input tokens per task (Appendix G).
5. Sample-and-judge, token-matched: five student samples, Granite picks one. Not run on Nano (Appendix H).
6. Seed program (hand-written, before search), Lightning only.
7. Ablation: Sonnet 4.5 proposes the program itself, no traces, no primitives, scored on task outcome (Section 5.6).

Is any baseline a text skill or note given to the same student? Partly. GEPA is text (an optimized system prompt) on the same student. But it is not a teacher-written note. It is written by gpt-4.1 from outcome scores, it is one prompt per student for the whole suite, and it is not built from any failure step. The ReAct arm also feeds the student text, but the text comes from the weak 8B model. There is no arm where the teacher or a frontier model writes a short advice note.
There is also no teacher or frontier-model row on the test sets. So there is no "rent" baseline.

## Results (including weak and negative ones)

Table 2, accuracy %, Retail / Telecom / LiveMCP / Avg:
- Vanilla: Lightning 75.4 / 47.4 / 42.1 / 55.0. Nano 64.0 / 36.8 / 45.3 / 48.7. Super 79.8 / 51.8 / 33.7 / 55.1.
- SFT: Lightning 72.8 / 47.4 / 44.2 / 54.8. Nano 76.3 / 50.9 / 43.2 / 56.8. Super 86.0 / 50.0 / 56.8 / 64.3.
- GEPA: Lightning 79.8 / 51.8 / 46.3 / 59.3. Nano 71.9 / 54.4 / 44.2 / 56.8. Super 80.7 / 57.9 / 40.0 / 59.5.
- ReAct: Lightning 71.9 / 32.5 / 16.8 / 40.4. Nano 64.0 / 28.1 / 17.9 / 36.7. Super 69.3 / 28.1 / 23.2 / 40.2.
- Sample-and-judge: Lightning 82.5 / 55.3 / 42.1 / 60.0. Super 83.3 / 46.5 / 58.9 / 62.9.
- PLVR final: Lightning 82.5 / 94.4 / 50.5 / 75.8. Nano 83.3 / 93.3 / 45.3 / 74.0. Super 79.8 / 93.3 / 54.7 / 75.9.
- PLVR seed (Lightning): 72.8 / 68.4 / 37.9 / 59.7.
- Granite-4.2-8B vanilla: 77.2 / 43.0 / 28.4 / 49.5. Granite under PLVR: 82.5 / 91.2 / 42.1 / 71.9.

Student size:
- Under the program the three Nemotron students land within 1.1 points on Telecom and 3.5 on Retail. Untreated they were 15.0 and 15.8 apart. On LiveMCPBench the spread barely moves: 11.6 to 9.4 (Figure 3a, Section 5.1).
- The 8B student is 2.1 to 3.2 points below the Nemotrons on Telecom, within 2.7 on Retail, and 3.2 to 12.6 below on LiveMCPBench.
- Size is not a clean capability axis here. Untreated Granite-8B (77.2 Retail) beats untreated Nano (64.0) and Lightning (75.4). Untreated Super is the worst on LiveMCPBench (33.7).
- GEPA (text) helps the weakest student most: Nano Telecom 36.8 to 54.4, Retail 64.0 to 71.9 (Section 5.3).

Weak and negative results:
- Retail: PLVR is level with sample-and-judge on Lightning (82.5 both) and 3.5 below it on Super. PLVR on Super Retail equals vanilla (79.8). SFT on Super Retail is best (86.0).
- LiveMCPBench: PLVR on Nano equals vanilla (45.3). Sample-and-judge beats PLVR on Super (58.9 vs 54.7). SFT beats PLVR on Super (56.8 vs 54.7).
- The ReAct loop is below vanilla in 8 of 9 cells and equal in one. Feeding the student a weak model's plan made it worse (Section 5.4).
- The hand-written seed program is below vanilla on Lightning Retail (72.8 vs 75.4) and LiveMCPBench (37.9 vs 42.1).
- SFT is below vanilla in three cells (Lightning Retail, Super Telecom, Nano LiveMCP).
- Ablation (Table 3, Lightning): a program proposed by Sonnet 4.5 with no traces and no primitives gets 77.2 Retail and 75.4 Telecom, against 82.5 and 94.4. So on Telecom the seed gives +21.0 over vanilla, frontier prior knowledge +7.0 more, traces and primitives +19.0 more.
- Cost: a run under the program costs 4.7 to 9.8 times the FLOPs of a vanilla run. 100 to 117 Granite calls per task. The student reads 248,100 to 255,900 input tokens per task against 45,907 to 76,916 untreated (Table 7, Section 5.7).

Does the paper separate "limited capability" from "missing procedural knowledge" with evidence?
Only indirectly, at the suite level. The test is: if one fixed program makes weak and strong students score the same, the gap was procedure. Evidence for: Telecom spread 15.0 to 1.1, and the 8B model reaches 91.2. Evidence against a clean split: (a) the authors say the estimate is an upper bound, because the program also carries the frontier models' prior knowledge and a hand-written seed (Section 6, Limitations). (b) The program adds about 100 extra small-model calls per task with verifiers, so it adds computation and decomposition, not only knowledge. The token-matched arms control for raw budget, not for decomposition. (c) There is no per-task or per-failure labelling of "procedural" versus "capability". (d) GEPA, which is procedure written as text, reaches at most 57.9 on Telecom. So "procedure can be written down" (Section 1) is shown only for the executable, verified form.

## Limitations

Authors' (Section 6, Scope):
- The gain is not due to traces alone. Seed, Opus and Sonnet all add knowledge.
- Single runs for nearly every cell. Differences of a few points are not resolved.
- Training tasks share domain, tools and policies with the test suites. Only in-domain generalization is shown. No cross-domain transfer.
- Needs intermediate outputs that can be checked. Open generation is out of scope.
- One teacher, three task types.
- The trace-free ablation covers Retail and Telecom only.

Mine:
- No frontier or teacher row on the test sets. We cannot tell how close 94.4 is to the teacher, or whether the program beats simply renting the teacher.
- With n = 114 one task is 0.88 points and the binomial standard error near 80% is about 3.7 points. Most Retail and LiveMCP differences are inside noise.
- The "program" is not a plain function. It makes 100 to 117 LLM calls per task. The comparison with text advice is therefore confounded with extra compute and with verifiers.
- The text arm (GEPA) differs from the program arm in author model, in training signal (outcome vs process distance) and in budget. So text vs program is not a controlled contrast.
- Search used Lightning as the student. "Same program for every student" could still favour models like Lightning.
- The cost of writing tasks (Opus), running the teacher (Kimi-K3 on 553 tasks) and writing primitives (Opus) is not reported. Only Granite scoring and Sonnet mining are.
- GEPA validation exact-match was 0.81 to 0.95 on synthetic data while test accuracy stayed at 40 to 80. So the synthetic validation signal used for selection is a weak proxy for the benchmark.
- Table 7 pools 278 tasks for some vanilla rows and 228 for program rows. The token comparison is not on identical task sets.
- Nothing is released. Appendices give summaries, not code.

## Assumptions not tested

- That closing the spread between students measures "procedure" rather than added compute, verification or decomposition.
- That the teacher's action sequence is the right reference process (only successful teacher traces are kept, and one path per task).
- That rules mined from telecom and tool-search traces are the right candidate set for retail.
- That one program per task family stays valid when tools or policies change.
- That 8B is "small enough". No student below 8B, and no student is shown failing under the program.
- That results hold with a different primitive executor than Granite-4.2-8B.

## Mapping to Loopy components

- C1 (forms compared, same failure, same teacher, same student): PARTLY. Text (GEPA prompt) and program are both run on the same students and the same task suites (Table 2, Sections 5.3, Appendix I). But different authors, different training signal, suite level only, never the same failure, and the program also adds about 100 LLM calls. Weights (SFT) is a third form (Section 5.2).
- C2 (student strength): PARTLY. Four frozen students from 8B to 120B. Finding: student matters little under the program on Telecom and Retail, still matters on LiveMCPBench (Section 5.1, Figure 3a, 3b). No analysis of when text is enough versus when a program is needed. No student weak enough to break the program.
- C3 (predict before paying): NOT. No predictor, no teacher diagnosis, no self-forecast, no trace features. The only statement is after the fact: "how much is procedure depends on the domain" (Section 6).
- C4 (economics over repeats): PARTLY. Units are tokens, calls and FLOPs. Build cost given for search (3.0e19 FLOPs, 383,783 calls, 1.87B tokens) and mining. Per-task cost 4.7 to 9.8 times vanilla (Section 5.7, Appendix C, Tables 7, 8). No dollars, no wall time, no break-even, no failed-build accounting, no comparison with the cloud model doing the task.
- C5 (online per-task choice among rent, coach, compile): NOT. One program per task family, built offline, applied to every task.
- C6 (harm): PARTLY. Suite-level harm is visible but not studied: ReAct below vanilla in 8 of 9 cells, seed program below vanilla on two suites, SFT below vanilla in three cells (Table 2, Section 5.4). PLVR is never below vanilla (two ties). No per-task harm analysis.

## What this means for Loopy

What we can no longer claim:
- That we are first to show a program built from a strong model's traces lets a small frozen model match larger ones on procedural tool tasks. PLVR shows 43.0 to 91.2 on an 8B model.
- That we are first to pose "capability or missing procedure" for small tool-use agents. That is PLVR's opening question.
- That a program beats prompt optimization and fine-tuning at the suite level. PLVR shows it on Telecom (program 93 to 94, GEPA at most 57.9, SFT at most 50.9).

What stays open (and PLVR makes sharper):
- A controlled text-versus-program contrast: same teacher, same failure, same student, same budget. PLVR's GEPA arm is not that.
- Any prediction of which remedy will work. PLVR only reports the domain-level outcome after building.
- Economics against renting. PLVR has no teacher row and no break-even. Its program raises inference cost 5 to 10 times, so it is an accuracy purchase, not a cost saving. Loopy's compile (a function the small model only calls) is a different object and can be cheaper per repeat. Say this difference clearly.
- Per-task, online choice. PLVR is per family, offline, from 553 synthetic tasks and 539 traces.
- Our pilot result "labelled procedural, yet the note failed" fits PLVR's own numbers: text procedure (GEPA) stalls near 52 to 58 on Telecom while the executable form reaches 93 to 94. PLVR does not isolate why. That gap is a Loopy question.

Design lessons to copy:
- Token-matched baselines, so "the program just spends more compute" is answered.
- A seed versus final versus trace-free ablation, to show what the teacher's traces add beyond the builder's prior knowledge.
- Verifier plus fallback on every compiled piece.
- Report the spread between students as well as the mean.
- Overlap guards between build tasks and test tasks, stated as a numbered list.
- Say which cells are single runs and refuse to rank inside noise. With our 9 tasks this matters even more.
- Add a cloud-model row. PLVR's missing teacher row is the first thing a reviewer will ask us for too.
