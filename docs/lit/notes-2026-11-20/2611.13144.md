# Teaching the Harness: Student-Aware Skill Transfer for LLM Agents

- arXiv: 2611.13144v1, 9 Nov 2026. Chang Liu, Bo Wu (Colorado School of Mines). No code link in the paper.
- Read on 2026-11-20 from the arXiv HTML text dump (2536 lines) and the 25-page PDF.
- Section, table and figure pointers below refer to the paper. "My reading" marks anything the paper does not state outright.

## Claim

A strong teacher model writes better text skills for a fixed weak student when it first builds a model of that student. The method is Student-Aware Teaching (SAT). The teacher keeps a profile of what the student does, a list of hypotheses about why it fails, runs small probe tasks to test them, then writes short skills. A skill is kept only if it raises the student's success on matched development tasks. After that the teacher leaves and the student runs with the saved library.

Key number: Claude-Sonnet-5 teaching DeepSeek-V4-Flash reaches 86.46% acceptance, vs 81.04% for a teacher with the same loop but no learner model ("agnostic") and 75.00% with no skills. Mean of four runs, SAT ahead in each (Table 2, Section 5.1).

Second numbers: with a deliberately wrong student profile, 0 of 48 candidate skills pass admission (Section 5.1, Table 24). Frozen libraries keep +5.6 to +11.1 points after the teacher is gone (Table 6). The teacher costs $0.39 per run (Table 29).

## Method (enough to reproduce)

Learner = student model + harness. Weights and harness code stay fixed. Only a text skill library changes (Section 3.1).

Per teaching round (four rounds in the main setting, Section 3.2, Appendix A):
1. Observe. The student attempts a batch of teaching tasks with its current library.
2. Empirical profile. Per task category a Beta-Bernoulli count starting at alpha = beta = 1, plus failure labels and short notes (A.1).
3. Analytical learner model. A text summary and a bounded list of hypotheses. Each has a claim, a confidence, evidence and a status, plus fields for measured task boundaries (A.1). It also outputs a predicted probability that the bare student solves a given task.
4. Probes. The teacher asks for variants of one task family with one property changed (inventory size, file count). The bare student runs each. A pass-then-fail transition is stored as a "sampled boundary". All-pass, all-fail and non-monotonic sweeps are "inconclusive" (A.2).
5. Skill generation. Up to three candidate skills per round. Each is a text procedure of at most 900 characters with a target category and metadata. Four native types (content, process, affordance, plan), all text. The prompt gets up to six task descriptions and four failed traces. The aware prompt also gets the profile, the learner model, weak-category priorities and probe results. Copying task answers is forbidden (A.3).
6. Admission. Each candidate runs on 1 to 4 development tasks from its category, once with the candidate alone and once with an empty library, temperature zero. Utility = mean of (with minus without) (Eq. 2). Positive utility admits it. At most two active skills per category. It can replace a generic seed skill. Interference on up to two off-category tasks is logged but not used (A.4).

Both teachers start from the same six generic skills (Appendix B).

Deployment (Section 3.3, A.5). Teacher removed. Three ways to deliver skills: student selection (the student picks up to two from a menu), category routing (a rule matches the task's category tag and picks up to two by utility; logs call it "oracle"), flat injection (every active skill). Skills are advice placed before the task text. The student chooses its own actions.

Strong-model calls: 82.67 teacher calls per run for SAT (119,400 input and 15,304 output tokens, $0.392) vs 76.00 for agnostic ($0.231). Mean of runs S2 to S4 (Table 29).

Validation by re-running the weak agent: yes, the admission test. But 8 of the 12 full aware skills were admitted on a single development task (C.6).

Form of the transferred knowledge: text only. Controller-enforced plans exist in the code but are "left for future evaluation" (A.3).

## Setting, benchmarks, models

- AppWorld: not used.
- Five generated task suites, each with a programmatic verifier (Section 4, Table 8): Terminal (rename, merge, dedupe, CSV filter, file pipelines), Inventory API (restock every item below a threshold through list, query and restock tools), Arithmetic word problems, Python code (implement, bug repair), Dependent workflows (file stage chains). The Inventory API suite is the closest thing to our API tasks.
- Later tasks come from the same task families seen in teaching (Section 3.1). So tasks repeat in kind, as in our setup.
- Base harness (Appendix B): asks for a plan, then a tool loop of at most 10 iterations, one tool call each. Tool output cut to 400 characters. Context keeps the system message and the last six messages.
- Main setting S1 to S4: 60 teaching tasks, 30 development tasks, 60 test tasks (12 per suite), each test task run twice (Table 9).
- Extended run: eight rounds, 200 teaching tasks, 150 test tasks x 2 (Appendix G).
- Teachers: Claude-Sonnet-5; local Qwen3-14B, Qwen3-32B, Qwen2.5-32B-Instruct.
- Students: DeepSeek-V4-Flash (main), Gemini-3.8-Flash, GPT-5.4-Mini, Qwen3-8B, Qwen3-1.7B, Qwen2.5-7B-Instruct, Qwen2.5-3B-Instruct.
- Also: four production harnesses (Codex, Pi, OpenCode, Claude Code) with the DeepSeek backbone; MATH and GSM8K subsets; a self-teaching comparison.

## Metric

Acceptance: each test task runs twice. Task score = share of its two runs the verifier accepts (0, 0.5 or 1). Acceptance = mean task score over held-out tasks, as a percent, at the final teaching round, fixed in advance (Appendix J, "Evaluation protocol"). Teacher prediction quality: Brier score and AUROC for predicting bare-student success on a fixed panel of ten tasks (A.6). Paired 95% intervals by task-paired bootstrap for the side experiments, not for the primary table.

Ablations and controls:
- Run S2 (Tables 3, 23): full SAT 87.5 (Brier 0.041). No fine probes 83.3 (Brier 0.036). No analytical learner model 83.3 (Brier 0.180). Each ran as its own job with its own baselines, so the authors call the differences "indicative".
- False profiles (Table 24): two seeds each. 12 candidates per run, 48 total, none admitted. Final acceptance 75.0 (overestimating) and 79.2 (underestimating). Underestimating teacher's Brier about 0.75, AUROC below 0.3. Teacher cost $0.36 to $0.41 per run, the same as a good run.
- Library swap (Tables 5, 25): DeepSeek with its own library 93.3 vs Gemini's 83.3 under category routing, +10.0 [2.5, 18.3]. The other five comparisons are +1.7 to +4.2, and four of those five intervals touch or cross zero.
- Extended run (Table 20, Figure 2): aware 78.3 to 84.3 over eight rounds, agnostic 80.7, no skill 78.0 at the end. Aware vs no skill +6.3 [2.0, 11.0]. Aware vs agnostic +3.7 [0.0, 7.7]. 13 tasks better, 6 worse, 131 same. Teacher AUROC 1.0 in rounds 2 to 7.
- Teacher-free deployment (Tables 6, 15, 16): DeepSeek mean gains +5.6 (student selection), +8.6 (category), +11.1 (flat).
- Self-teaching (Appendix E): no skill 72.22, student teaching itself 81.94, self-aware 79.17, external strong aware teacher 83.33. The strong teacher's edge over self-teaching is one run out of 72.
- MATH (3 runs) 75.0 / 73.6 / 81.9. GSM8K (2 runs) 87.5 / 89.6 / 97.9. Verifier accepts the gold answer as a substring.
- Production harnesses (Table 26): aware +1.0 to +5.2 over no skill, all intervals touch zero.

Weak and negative results:
- Agnostic teaching below no skill: S1 (75.83 vs 79.17), Python code suite (87.50 vs 92.71), Qwen3-8B with the 14B teacher (33.3 vs 38.3), Qwen3 inventory (0% vs 8.33%), S4 inventory (50.0 vs 62.5), Claude Code harness final round -11.5 [-22.9, -1.0], first-round libraries in Pi (-22.9) and Codex (-11.5).
- Aware below agnostic: Arithmetic (-2.08), file pipeline (50.0 vs 66.67, Table 30), dependent workflow (94.44 vs 98.61), Gemini (91.7 vs 92.5), Qwen2.5-3B run A.
- Flat injection hurts Qwen2.5-7B: 29.2 vs 43.3, -14.2 [-27.5, -0.8] (Table 15).
- Qwen3-8B never picks a skill in 120 student-selection runs. Gain 0.0.
- Extended-run inventory: aware 55.0, agnostic 56.7, no skill 56.7 (Table 21). The skill is right but "the procedure still requires one update call per deficient item" (Appendix G). Advice cannot remove the step limit.
- Exact-word counting: 0.00 in all three conditions (Table 30).
- Skill-validation Brier is 0.250 aware and 0.253 agnostic (Appendix G, "Prediction quality"). A constant 0.5 forecast scores 0.25. My reading: the teacher predicts the bare student well but does not predict outcomes on the skill validation tasks better than a coin. The paper only says this "answers a different question".
- Noise floor: with a fixed generic library, acceptance ranges 71.7 to 82.5 across runs (H.2). The headline aware-vs-agnostic gap is 5.42.

## Limitations

Authors' (Section 6 "Scope", plus caveats in the text):
- Most evidence is one teacher and one student in one harness.
- Few seeds for controls. False profiles are extreme on purpose.
- Deployment results depend on the selector.
- Ablations ran as separate jobs, so differences are indicative.
- No single control isolates learner modeling as the cause.
- The learner model cannot help a student too small to follow procedures and adds little near ceiling.
- Category routing needs a category tag on the task.
- Admission often rests on one task (C.6).
- Cost for local models leaves out GPU time (Appendix J).

Mine:
- The primary table has no intervals. Four runs. S3's margin over agnostic (+0.83) is one run of 120. With their own noise floor (71.7 to 82.5 for a fixed library), +5.42 is suggestive, not established.
- The aware teacher spends about 70% more dollars and 2.2x the input tokens of the agnostic teacher (Table 29), and it gets extra student runs for probes. The comparison is not matched on budget. The authors name "matched replays" as future work.
- Tasks are synthetic and generated by the authors. Test tasks come from the same families as teaching tasks.
- Admission compares against an empty library, not the current one. Interference is logged, not gated.
- The teacher is never run as the task solver. So there is no "rent the strong model" arm and no measured strong-model cost per task.
- Skill annotation is one model-assisted pass (C.2).
- Student size and teacher change together in Table 7, so "mid-sized students gain most" mixes the two.
- The Brier panel is ten tasks.

## Assumptions not tested

- That text advice is the right channel. Never compared with a program or an enforced plan, although the code supports enforced plans.
- That the learner model, and not extra teacher budget and probe runs, causes the gain.
- That predicting bare-student success leads to picking skills that work. Their own skill-validation Brier (0.25) does not support it.
- That a pass on 1 to 4 development tasks means the skill helps. Most aware skills passed on one task.
- That gains hold for tasks outside the taught families.
- That teaching pays off against the strong model doing the work. Appendix K gives the formula, no numbers.

## C1 to C7

- C1 forms (text vs program): NOT. All skills are text of at most 900 characters, delivered as advice (A.3). Code skills appear only in related work (Table 1). Enforced plans are future work.
- C2 student strength: PARTLY. Seven students, list above (Table 7, Section 5.3). Shape: mid-sized gain, tiny models gain nothing, strong models near ceiling. It asks "can this student use text advice", not "when is a program needed". Teacher changes with student.
- C3 predict before paying: PARTLY. The teacher predicts whether the bare student will solve a task (Brier 0.041 to 0.079, AUROC up to 1.0, ten tasks; Tables 3, 20). Probes locate a size boundary before a lesson is written (A.2, C.4). But which skill will work is found by paying: the admission run. The teacher's forecast on skill validation tasks is at coin level (Brier 0.250, Appendix G). A student-side signal exists only by accident: Qwen3-8B never picks a skill (Table 6).
- C4 economics: PARTLY. Unit is dollars, tokens and calls by role (Table 29): aware teacher $0.39 per run, full aware condition $0.67, extended run teacher $1.245 (Appendix G). A full failed build is priced: false-profile runs cost $0.36 to $0.41 and yield no skill (H.2). Break-even formula over N later tasks is given (Appendix K, Eq. 3 and 4) but never filled in. Strong-model cost per task is not measured.
- C5 online choice: PARTLY, weak. Three ways to route skills to a task at deployment (Section 3.3, Tables 5, 6, 15). Best route depends on the student. No routing to the strong model. No choice among kinds of help.
- C6 harm: PARTLY. Many harm cases are reported (list under "Weak and negative results"), with intervals for some. The admission gate is the guard. No systematic harm analysis and no per-task harm rate, except 6 of 150 tasks worse under aware vs agnostic in the extended run.
- C7 execution gap: PARTLY. It is the paper's framing: the student "may know how" and still fail through the harness (Section 1). Measured by probes (passes at 2 items, fails at 5 or more; passes at 8, fails at 12 and 16), by tool-call counts in traces (C.4), and by students that do not move with any skill (Qwen3-1.7B). Fix offered: simpler text procedures (one bulk query). Where the procedure still needs too many calls, nothing fixes it (extended inventory stays at 55%).

## What this means for Loopy

What we can no longer claim:
- That a student profile or learner model for teaching a weak agent is new. That is this paper.
- That "the teacher can predict whether the student will fail" is new. Brier 0.04 on their panel.
- That the break-even formula over repeats is new. Appendix K has it, in dollars. What is still ours is measuring it.
- That admitting a note only after re-running the student is new.
- That "student strength decides whether advice helps" is new as a text-only finding (Table 7).

Design lessons to copy:
- Admission gate: run the student with and without the candidate on matched held-out repeats before keeping it. Our coach arm should have this.
- Probes: vary one property of the task (number of items, pages, records) to find where the student breaks. A boundary like "passes at 8, fails at 12" is a cheap feature for our predictor, and it separates "does not know the steps" from "runs out of budget".
- False-profile control and library swap are good templates for showing that help is student-specific.
- Run the no-help baseline inside every job, fix the reporting point ahead of time, run each task more than once, and report the noise floor of a fixed library.
- Price a failed build. Their wrong-profile runs cost the same as good ones and produced nothing.
- Report cost by role (calls, input tokens, output tokens, dollars), as in Table 29.

What stays open after this paper:
- Advice vs program. Their own negative case is the argument for it: correct advice, still 55% on inventory, because each update needs its own call. A compiled function that does the loop in one call is the direct test. Same for Qwen3-1.7B, which no text helps.
- Predicting which remedy will work before paying. They predict student failure, not remedy success, and their forecast on skill validation is at chance.
- A measured break-even against the strong model doing the task every time (our RENT arm). They never run it.
- A per-task online choice among rent, coach and compile.
- Real API benchmark (AppWorld). Their tasks are author-generated.
- Our pilot fits their story: the teacher's label ("procedural") does not tell you whether text will work. They needed probes and admission runs to find out.
