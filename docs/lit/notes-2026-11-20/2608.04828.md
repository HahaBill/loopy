# 2608.04828 — Skill-Use: Can LLMs Actually Use Skills in Agentic Harnesses?

Han, Xu, Liao, et al. (ECNU, HKUST, Fudan, Tencent Hunyuan). arXiv v1, 5 Aug 2026, cs.CL. 29 pages.
Repository named in the paper: github.com/JinyiHan99/Skill-Use-Bench.

## Claim (key numbers and where they are)

1. Frontier models do not use skills reliably. The best configuration, GPT-5.5 under Claude Code, reaches a Skill-Use score of 0.613 (Table 1).
2. Two separate bottlenecks. Trigger (does the agent open the skill) and Compliance (does it follow the procedure once opened). "Even among triggered traces, the highest Compliance† reaches only 0.638" (§4.2, Table 1).
3. Scores and rankings change with the harness (Claude Code vs Codex). Table 1, Table 6.
4. Putting the whole skill in context fixes triggering, not execution (§4.4, Fig. 4, Fig. 5).
5. A half-followed skill is worse than no skill. Paired task-completion gain is negative when Skill-Use is below about 0.5 (§4.7, Fig. 6d).

## Method, in enough detail to reproduce

Instance (§3.1). x = (skill s, user task q, sandbox E, hidden rubric R). Skill s = (m, p): m is name, short description and file path; p is the full procedure. The agent first sees only (q, E, m). It must decide the skill applies and open the file. This is "progressive disclosure".

Scores (§3.1):
- Trigger g = 1 if the agent retrieved the target skill in the trajectory, else 0. Deterministic.
- Compliance C = weighted share of prescribed skill requirements satisfied.
- Boundary B = weighted share of skill prohibitions respected.
- SU = g · [0.7·C + 0.3·B] (Eq. 2). Execution gets credit only after a trigger.
- Comp.† and Bound.† = the same, on triggered traces only. SU+ = 0.7·C† + 0.3·B† (I checked: 0.7·0.606 + 0.3·0.709 = 0.637, matches Table 1).
- Task completion is recorded by separate rubric items with weight 0. It is not part of SU.

Benchmark (§3.2, Fig. 1). 79 real skills, 177 tasks, 9 domains, 1,314 rubric items (mean 7.4 per task, range 3–16). Item types: Compliance 55%, Task-outcome 20%, Evaluability gate 13%, Boundary 12% (Fig. 1c). Mean of 4.8 skill-exclusive requirements per task (text; the figure says 4.7), up to 12.

Construction (§3.3, App. B):
- Skills: 105,586 public GitHub skills → 15,000 (stars ≥ 5, dedupe) → fetch about 1,500 → 1,000 → rule scoring keeps 400 (constraint density ≥ 0.30 and style specificity ≥ 0.25) → masked-skill evaluation keeps 80–150 → 79, plus entries from SkillsBench and SkillLearnBench (Table 3).
- Masked-skill check: hide the skill, ask whether a strong model would do the same thing from the prompt and common practice. If yes, the requirement is "generic" and dropped. Only "skill-exclusive" requirements are scored. Run once per skill and once per task-requirement pair.
- Tasks: real assets, the prompt hides the procedure, no tool names or formats in the prompt, reference solutions kept on the evaluator side.
- Rubrics: deterministic checks first (state diff, regex anchored to tool-call fields). LLM judge (GPT-5.4, temperature 0) only where a rule cannot express the check. Binary verdict, one item at a time, judged twice, one re-adjudication (Table 4, Fig. 20). Rule weights: headline 1.0, important 0.5–0.75, soft 0.25 (Fig. 14). LLM-judge share of scored weight should stay below 30% (Fig. 18, Fig. 19).
- Review: multi-agent, reviewers from different model families, proposer / attacker / aggregator (App. B.4, Figs. 15–19).
- Human audit (App. C): one task per skill, 79 triples, five crowd annotators. On 100 items, pairwise agreement 86/100, Cohen's κ = 0.65.

Runs (§4.1, App. D). Eight models, two harnesses. Temperature 0, top-p 1.0, reasoning effort "high" where offered. Fresh Ubuntu 22.04 Docker container per task. Turn limit 120 (Claude Code) and 80 (Codex). Wall clock 1,500 s. About 2.8% of traces failed infrastructure checks and were rerun. Gemini is excluded because its channel broke the Skill tool.

Extra experiments:
- Injection mode (§4.4), Codex only: native (name, one-line description, path) vs preloaded (full skill text in the initial instructions), paired per task and model.
- Library size (§4.5), Claude Code: N in {1, 10, 20, 30} skills, the target always present, the rest random distractors. Outcome: correct / wrong / none.
- Out of scope (§4.6): 53 tasks that overlap a skill's topic but do not need its procedure. Six models. Avoidance = share of tasks where the agent does not invoke the skill.
- Task completion (§4.7), Claude Code: 779 triggered runs, each paired with a no-library run on the same task and model. Mean paired gain TC_skill − TC_base by SU bin.
- Judge noise (App. E.5): 83 (task, model) observations rescored three times.
- Weight sweep (App. E.6): α in {0.25, 0.5, 0.7, 0.75}.

## Setting, benchmarks, models

- Benchmark: Skill-Use (new). **AppWorld is not used.** Domains (skills, tasks): Frontend and Mobile 11/28, Software Architecture 11/24, DevOps and Infrastructure 8/23, Content Writing 8/22, Data Science 14/20, Document Processing 7/17, Database 8/17, Security 8/15, Business Operations 4/11.
- Models: Claude Opus 4.7, Claude Opus 4.8, GPT-5.5, DeepSeek-V4-Pro, GLM-5.1, MiniMax-M3, Kimi-K2.6, Qwen3.6-Max. All large or frontier. **No small model.** No parameter counts.
- Harnesses: Claude Code and Codex.
- Skills are human-written community documents. No teacher model. No skill is built from a failure.

Main readings:

## Limitations

Authors': none in a limitations section. They state that judge noise is concentrated in mid-range traces (App. E.5), that Qwen3.6-Max's library curve is a lower bound because of the turn limit (App. E.3), that Gemini was excluded (App. D), and that the benchmark "is not a certification of safety or deployment readiness" (App. G).

Mine:
1. No weak models. All eight are large. The paper says nothing about small students.
2. SU does not measure task success. Task completion has weight 0. Absolute task-completion rates are never reported, only the paired gain by SU bin.
3. Compliance is scored only on requirements a strong model would not do by default (the masked-skill check). So the benchmark measures obedience to counter-default rules. It may overstate the execution gap for skills that mostly encode what a good agent would do anyway.
4. My derivation from Table 1 (Claude Code). For the four low-trigger models, all-trace Compliance implies that traces which never opened the skill still score about 0.37–0.38 on Compliance (for example DeepSeek: (0.439 − 0.324·0.588) / 0.676 = 0.37). Triggered traces score 0.58–0.64. So opening the skill adds only about 0.2–0.27 Compliance, and "skill-exclusive" items are met about a third of the time without the skill. Caveat: untriggered tasks may be a different mix of tasks.
5. Table 1 is not consistent with its own gated definition for three Claude Code rows. Mean SU must equal Trigger × SU+. DeepSeek: 0.324 × 0.621 = 0.201, reported 0.250. GLM: 0.206 vs 0.267. Qwen: 0.271 vs 0.318. Table 7 (α = 0.7) gives 0.195, 0.202, 0.262, which match the product. Tables 1 and 6 appear to overstate these three by about 0.05–0.065. The top models are unaffected.
6. Fig. 6d bins are suspiciously symmetric (−5.4, −2.7, +2.7, +5.4) and have no n per bin and no intervals. SU is measured after the run, on the same trace, and is itself partly judged by an LLM. The relation is a correlation, not an effect of compliance. Easy tasks may produce both high SU and high completion.
7. 779 triggered Claude Code runs does not match Trigger × 177 × 8 (about 910). The subset is not explained.
8. Fig. 6c includes a model labelled Gemini, although App. D says Gemini is excluded from every analysis. Avoidance differs by 0.04 across models (about 2 tasks of 53), so the "negative rank correlation" rests on very little.
9. Trigger under the preloaded mode is not defined. There is nothing to retrieve when the text is already in context, yet Fig. 4 reports preloaded trigger rates below 1.
10. Judge reliability is moderate: ICC 0.53 for SU, human κ 0.65.
11. Fig. 2's caption says "one in-scope task per skill, giving 177 tasks" for 79 skills. The counts imply 2.2 tasks per skill.
12. One harness-specific confound: the turn limit differs (120 vs 80).
13. Temperature 0 and one run per task. No run-to-run variance of the agent is measured, only of the judge.

## Assumptions not tested

- That following the skill is the right thing to do. Skill quality is assumed. Task completion is a side channel.
- That the masked-skill check with "a strong model" cleanly separates skill-exclusive from generic behaviour (see my point 4).
- That Trigger and Compliance are independent bottlenecks. They are measured on different subsets of tasks per model, since Compliance† exists only where the model triggered.
- That preloading equals "skill in context" for execution purposes on all skills. Fig. 9 shows it hurts on some.
- That results on frontier models carry over to smaller ones.

## C1 to C7 mapping

- **C1 forms of help: not.** One form only, a text skill document. The closest hint is Fig. 3: procedures that name a tool, a format or a defined operation are followed better than open-ended ones. That is a property of the text, not a text-vs-program test.
- **C2 student strength: partly.** Eight models, all results in Table 1. No size axis and no weak model. The useful fact: once the skill is opened, Compliance under Claude Code is 0.58–0.64 for every model, so the execution gap is not only a weak-model problem.
- **C3 predict before paying: not.** Only after-the-fact correlates: skill category (Fig. 3), abstract vs keyword-rich skill name for triggering (Fig. 9), SU bin for task-completion gain (Fig. 6d). No predictor is built or scored.
- **C4 economics: not.** No tokens, dollars, calls or time. Turn and wall-clock limits are caps, not costs.
- **C5 online choice: not.** The agent's own decision to open a skill is studied (Trigger, library size, out-of-scope avoidance). There is no routing to a stronger model and no choice among remedies.
- **C6 harm: covered.** Task completion falls below the no-skill baseline when SU < 0.5 (Fig. 6d: −5.4 and −2.7 points). Preloading lowers SU on some skills by up to 0.30 (Fig. 9). Skills are invoked on about half of out-of-scope tasks (Fig. 6c, Table 9).
- **C7 execution gap: covered, best single source.** Measure: Compliance† and SU+ on traces where the skill was retrieved; rubric of skill-exclusive items checked on the trajectory and artefacts. Size: 0.576–0.638 under Claude Code, 0.304–0.626 under Codex (Table 1). Sham-trigger rate 15–42% (Fig. 8b). By model size: not available, all models are large. Fix: none. Preloading the full text does not help execution (Fig. 5).

## What this means for Loopy

What we can no longer claim as new:
- That an agent with the right skill in context often does not follow it. This is the paper's main result, with a process-level metric, on frontier models.
- That a skill can lower task success. Fig. 6d says partial use is worse than none.
- That "skill in context" does not mean "skill used".

Design lessons to copy:
- Measure compliance with the note apart from task success. For each coach note, write a few checkable items (which API, which argument, which order) and score them from the tool calls. Then COACH failures split into "did not follow the note" and "followed it and still failed". Our pilot cannot tell these apart today.
- Score from tool-call fields and artefacts, never from the agent's narration (Table 5: judges credited models that described the behaviour and never did it).
- Add the cloud model with the coach note as an arm. Their data say even frontier models comply at about 0.6. If the cloud model also ignores our notes, the problem is the note, not the student.
- Always run a no-help arm on the same task so harm is visible. Our small model scores 0/9 alone, so harm cannot show. We need tasks where the small model sometimes succeeds alone.
- Report the harness. Their rankings move with it.
- Rescore a subset several times and report judge agreement if any item is LLM-judged. Prefer AppWorld's deterministic state checks.
- Concrete, tool-named procedures are followed better than open-ended ones (Fig. 3). This supports testing a graded axis from loose advice to exact steps to a callable function, not only two points.

What stays open after this paper:
- Everything about weak students. No small model is tested.
- Any fix for the execution gap. They measure it and offer none. COMPILE is a candidate fix nobody here tests: move the procedure out of the text the agent must obey and into a function it only calls.
- Forms of help, teacher-built help, cost, repeats, routing, prediction. None are in scope.
- AppWorld. Not used.
- One caution for our framing: this paper locates most of the between-model gap in Trigger, not execution. In Loopy the note is always in context, so Trigger is not our variable. But a compiled function must also be chosen and called. We should log whether the small model calls it at all, the same way they log Trigger, and test with more than one function in the library (their drop from N=1 to N=10).
