# 2610.33024 — Evolving to Match Capabilities: Improving Harness Self-Evolution via Skill Adaptation

Yang, Wang, Wu, et al. (UCAS, UCSC, Tsinghua, NUS, ISCAS). arXiv v1, 10 Oct 2026, cs.LG. 24 pages.
Project page named in the paper: zhihaoyang30.github.io/skill-adaptation. Code promised "after review", not released.

## Claim (key numbers and where they are)

1. The same human-written skill helps strong models and does not help weak ones. On 103 selected task-skill pairs, the skill lifts GPT-5.6-luna by +31.1 points and lowers Gemma-4-E4B by 8.8 points (abstract; Fig. 3b).
2. The weak models fail with the answer in front of them. "86% of weak-model runs that still fail with the skill violate a requirement already stated in the injected SKILL.md" (§3.1).
3. A fixed rewriting protocol (the "meta-skill") lets a strong model rewrite the skill so weak models can use it. Kimi-K3 with the meta-skill raises the three weak executors by +5.1 to +14.1 points over the original skill (Table 1). The meta-skill adds +5.1 to +6.0 over a one-sentence rewrite instruction (Fig. 5).
4. In a five-round self-rewrite loop, the meta-skill arm ends +2.0 to +5.1 points above the no-meta arm on all seven executors (Table 4, Fig. 6, Fig. 8).
5. Text has a ceiling. "What the meta-skill cannot repair is the executor" (§4.3).

## Method, in enough detail to reproduce

Setting (§2). Task T_i comes with a human-written skill S_i. Score s_m(T,S) in [0,1]. Skill gain Δ_m(T) = s_m(T,S) − s_m(T,∅).

Tasks (§2.1, App. A, Table 3). 607 tasks that ran reliably: SkillsBench 87 (OpenHands harness, deterministic tests), DocOps 186 (Claude Code, document-state checks), Tessl 334 (Claude Code, LLM judge with rubric).

Two conditions (§2.2). Without skill: task text and environment only. With skill: the full skill is placed in context. No retrieval, no progressive disclosure.

Pair selection (§2.3, Eq. 1). Tier gain Δ_G is the mean over models in the tier. Tier G "benefits" if Δ_G ≥ 0.10 and Δ_G − Δ_W ≥ 0.10. A pair is "skill-sensitive" if the frontier tier benefits, or if frontier is saturated without the skill (≥ 0.95) and the moderate tier benefits. Pairs where the weak tier already scores ≥ 0.80 with the skill are dropped. Result: 103 pairs (32 SkillsBench, 32 DocOps, 39 Tessl).

Failure labelling (§3.1). For each of the 103 pairs, read the three weak-model trajectories with the skill. Label the first observable failure. 131 labels on 103 pairs (labels can overlap):
- Tool execution (EXE), n=51: no deliverable; one or two tool calls; treats a file format as a tool; stops on a tool error.
- Instruction following (IF), n=35: output produced, requirement already in the skill is unmet.
- Context management (CTX), n=28: treats the skill's examples as the task, or saves to the wrong path. In the meta-skill text CTX is defined as "It succeeded without the skill and failed with it".
- Verification (REF), n=17: all parts present, value wrong, no check in the trajectory.

Meta-skill (§3.2, full text App. C). A fixed system prompt for the rewriter. "First locate the break, then fix that." One prescription per class:
- EXE: say which names are callable and which are documents; add an environment preflight; give a fallback; "Give commands the agent can run verbatim."
- CTX: state the task, the allowed scope and the delivery path early; say the rest is reference; inline needed content.
- IF: each requirement as one line "action — target — completion condition", with the negative branch. "Writing more about the requirement does not help; the text was already there."
- REF: end with a check: re-read the artefact from disk, recompute by a second route, compare to a threshold, loop.
Rules: no invented names, no pasted answers, return NO_CHANGE if no grounded improvement. Written with Claude-Opus-5 as assistant.

Protocol (App. B, Algorithm 1). Rewriter gets: task instruction, executor tool list, current SKILL.md files, and (self-evolution only) last score, a trajectory digest and the verifier output. Output: whole new files, or NO_CHANGE. Two gates. Loadability: file non-empty, name unchanged, ≤ 64,000 characters. Answer leakage: tokens that appear in hidden tests or the reference solution and nowhere in public material are blocked (one expected value or two identifiers rejects the rewrite). A rejected rewrite falls back to the old skill and the cell is still scored. One retry on a parse error.

Experiment 1, "skill adaptation" (§4.1). Strong rewriter, no execution evidence, one rewrite, one executor run. Rewriters: GPT-5.6-sol, GPT-5.6-luna, GLM-5.3, Kimi-K3, plus each weak executor rewriting its own skill. Executors: Qwen3.6-flash, Gemma-4-E4B, Qwen3.5-9B. All 103 pairs.

Ablation (Fig. 5). Same rewriter (Kimi-K3), meta-skill replaced by "Rewrite this skill so that it works for all models."

Experiment 2, "self-evolution" (§4.2). Rewriter = executor. Five rounds. Linear chain, no best-round pick, no rollback. Baseline: the same executor reruns the original skill in the same time window. Control arm: same loop, system prompt without the meta-skill. Seven executors: the three weak ones plus Qwen3.5-27B, Gemma-4-26B, Qwen3.5-plus, Kimi-K2.5.

Every model–task–condition cell is run once (App. B, "Scoring conventions").

## Setting, benchmarks, models

- Benchmarks: SkillsBench, DocOps, Tessl. **AppWorld is not used.** Tasks are file, document and developer tasks, not stateful API tasks.
- Models in the with/without study (tiers set by no-skill score): weak = Gemma-4-E4B, Qwen3.5-9B, Qwen3.6-flash; moderate = GPT-5.4-mini, Claude-Sonnet-4.6; frontier = GPT-5.6-luna, Claude-Opus-5.
- The paper gives no parameter counts. Sizes are only what the names imply.
- Skills are human-written (expert or vendor). There is no teacher that builds help from a failure. The "teacher" only rewrites an existing skill.

## Metric

Native benchmark score normalised to [0,1], averaged over pairs. SkillsBench: deterministic verifier. DocOps: document-state check. Tessl: LLM judge rubric score, used directly. Gains are differences of means. No confidence intervals. No significance tests. One run per cell.

Residual failures (§4.3). The rewritten skill "states the right procedure and the executor does not carry it out: it edits a script without rerunning it, repeats a failed call, stops before writing the artefact, or, when a task has several constraints, keeps the one the skill highlights and drops the rest."

My derived comparisons (not in the paper):
- Gain over the same-window rerun baseline at round 5 with the meta-skill: Qwen3.6-flash +0.121, Gemma-4-E4B +0.043, Qwen3.5-9B +0.052, Qwen3.5-27B +0.161, Gemma-4-26B +0.045, Qwen3.5-plus +0.166, Kimi-K2.5 +0.188. Stronger executors gain more from self-rewriting than the weakest ones.

- After the best text adaptation the weak tier sits at 0.17 / 0.37 / 0.62. The frontier tier with the original skill sits at about 0.88. Text closes a small part of the gap.

## Limitations

Authors' (§6): skills are already in context, so no retrieval and no progressive disclosure; multiple skills are scored as a bundle; fixed budget of five rounds; no parameter updates. Single run per cell, stated in §4.2 and App. B.

Mine:
1. Selection on the outcome. The 103 pairs were chosen because strong models gained at least 0.10 more than weak ones. The headline gap (+29.2 vs +1.2) is true by construction on this subset. On all 607 tasks there is no tier pattern (Fig. 3a).
2. Regression to the mean. Pairs were also kept only if the weak tier scored below 0.80 with the skill. Gemma-4-E4B's "original" score is 0.029 in Table 1 and 0.104 when the same skill is rerun later (Table 4 base). That 0.075 swing is larger than the meta-skill effect in the loop (+0.051). So part of the one-shot gain for Gemma (0.029 → 0.170) may be noise. Against the rerun base it is +0.066, not +0.141.
3. No held-out tasks. The meta-skill was built from the same 103 pairs and the same three weak models it is tested on. Only the four extra executors are held out, and only as models.
4. Per-task adaptation, tested on the same task. The loop rewrites a skill for task T and then scores it on T again. There is no fresh instance of a repeating task. The authors call it "per-task adaptation" (App. E).
5. The 86% figure has no stated procedure: who judged, on how many runs, with what agreement.
6. No statistics. One run per cell, no intervals. Several per-benchmark gaps flip sign.
7. No cost of any kind is reported.
8. Tessl scores are near ceiling for the stronger executors (0.94–0.99), which hides differences there.
9. The meta-skill system prompt says the agent "has already tried this task once", yet it is used unchanged in the one-shot setting where no attempt was made. It also says "602 measured model-task cells" while the paper says 607 tasks.
10. Size does not order the models. Gemma-4-26B (base 0.075) scores below Gemma-4-E4B (0.104). The "capability" axis is no-skill score, not parameter count.

## Assumptions not tested

- That the failure of weak models is a property of how the skill is written. The residual failures (§4.3) say part of it is not.
- That a text skill is the right carrier. No executable alternative is tried, although skills may ship helper scripts and the meta-skill itself pushes toward "commands the agent can run verbatim".
- That the first observable failure is the cause.
- That five rounds is enough, and that later rounds do not drift (some do).
- That gains on one run reflect a stable effect.
- That the answer-leakage gate (token matching) catches all leakage. A rewriter with verifier output can still encode task-specific facts (Fig. 9 names the answer cells).

## C1 to C7 mapping

- **C1 forms of help: not.** Every arm is text. The comparison is original text vs rewritten text (Table 1, Fig. 5). No program or tool arm.
- **C2 student strength: covered.** Seven models with and without skill (Fig. 3). Seven executors in the loop (Table 4). All results listed above. But it does not say when text stops being enough and a program is needed.
- **C3 predict before paying: partly, weak.** Base capability (no-skill score) is shown to go with skill benefit, on a selected subset only (Fig. 1a, Fig. 3b). The four failure labels are a diagnosis that picks a text fix, and Table 2 reports gain by label. Labels are assigned after reading failed trajectories. No predictor is scored. Table 2 has negative cells, so the label does not reliably predict that the fix works.
- **C4 economics: not.** No dollars, tokens, calls or time. One useful convention: a rejected or NO_CHANGE rewrite still counts in the mean (App. B), so failed builds are not hidden.
- **C5 online choice: not.** No routing. The only choice is revise vs NO_CHANGE.
- **C6 harm: covered.** Skill lowers Gemma-4-E4B by 8.8 points (Fig. 3b). CTX class = succeeded without the skill, failed with it (n=28). Weak self-rewrite lowers the average 0.294 → 0.271 (Table 1). One-sentence rewrite breaks a working skill (Fig. 12) and lowers Qwen3.5-9B (Fig. 5). Negative cells in Tables 2 and 4.
- **C7 execution gap: covered.** Measure: share of failed weak runs that violate a requirement already in the skill = 86% (§3.1). Size by model: Fig. 3b. Fix: rewrite the text to the executor (+5.1 to +14.1 one-shot; +2.0 to +5.1 in the loop). Ceiling: weak executors still fail to act (§4.3).

## What this means for Loopy

What we can no longer claim as new:
- That a weak agent fails with the right advice in context. This paper has it, with a number (86%), across three benchmarks.
- That the same help benefits strong models and not weak ones.
- That advice should be rewritten for the weak executor, or that a strong model should do the rewriting.
- That a weak model revising its own notes without guidance drifts or gets worse.
Our pilot result "teacher says procedural, student with the note still fails" is this paper's main observation. Cite it as prior evidence, not as our finding.

Design lessons to copy:
- Rerun the untouched baseline in the same time window as every treatment arm. Their own data show a 0.075 swing on a rerun.
- Add a "generic teacher" arm (their one-sentence instruction) so the effect of our coaching protocol is separable from the effect of a strong teacher.
- Answer-leakage gate on every teacher artefact. For COMPILE this matters more: a function can hard-code the answer for one instance. Test on fresh instances of the repeating task.
- Count failed and rejected builds in the mean.
- Write coach notes in their format: callable names vs documents, task and delivery path first, each requirement as action — target — completion condition, and a final read-back check. This is the strongest fair version of COACH. If COMPILE still wins against it, the form result is real.
- Label failures by the first observable break and report gains per label, including the negative cells.
- Report per capability tier, and define tier by no-help score.

What stays open after this paper:
- The form question (C1). They show text has a ceiling and stop there. "A skill can tell a weak executor what to do; getting it done depends on the model." Nobody here hands the weak model a function instead.
- Prediction before paying (C3). Their labels come after the failure and do not predict the fix reliably.
- Cost over repeats (C4) and any rent option (C5). Not touched.
- True repeats. They adapt and test on the same task instance.
- AppWorld and stateful API tasks. Not touched.
- A caution for us: their weak-tier gains from the best text adaptation are 5 to 14 points with one run per cell. Our 1/6 vs 5/6 is a far larger gap but on 6 tasks. We need their scale of n to say anything.
