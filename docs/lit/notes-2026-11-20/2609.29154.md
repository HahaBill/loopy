# SkillPivot: A Wrong Turn Does Not Ruin the Journey. Deviation-Guided Skill Self-Evolution for LLM Agents

- arXiv: 2609.29154v1, 24 Sep 2026. Feng (UCAS), Wang (USTC), Sun (Meituan).
- Read on 2026-11-20 from the arXiv HTML text dump (901 lines) and the 9-page PDF. There is no appendix.
- Section, table and figure pointers below refer to the paper. The paper uses "RQ1" to "RQ7" as section names.
- Tables 3 and 4 were garbled in the text dump (columns shifted). The numbers below come from the PDF.

## Claim

A failed agent run is usually not wrong from the start. It has a useful first part and then goes off course. Find the step where it goes off course (the "deviation point"). Let a stronger teacher continue from that exact step. Compare the student's failed ending with the teacher's successful ending. Write a small edit to the existing text skill from that comparison.

Key number: on ToolQA, mean success of a Qwen3-32B student rises from 53.18% to 59.36% after evolving over six task groups (Table 1). Other skill-evolution methods reach 53.85% to 54.85% (Figure 3a). On WildClawBench it goes from 34.35% to 73.00% after six rounds (Table 4). On LogicBench from 86.54% to 91.22% (Table 3).

## Method (enough to reproduce)

Starting point: the agent already has a good skill corpus (from SRA-Bench). The method edits it. It does not write skills from nothing.

Five stages (Method section, Figure 2).

1. Student rollout. The student runs a batch of tasks with the current skills, ReAct style, max 20 steps. An evaluator marks each run pass or fail. Passed runs go to a success pool, failed runs to a failure pool.

2. Deviation point detection. For each step t of a failed run compute V_t = 0.4 Exec_t + 0.3 Prog_t + 0.3 Div_t (Eq. 6).
   - Exec: rule-based. Did the tool call run and return something usable.
   - Prog: cosine similarity (all-MiniLM-L6-v2) between the observation and the ground-truth answer, counted only when it beats the best earlier step (Eq. 7). This uses the gold answer.
   - Div: 1 minus the highest similarity between this action and any earlier action (Eq. 8). Low means the agent is repeating itself.
   - The step with the lowest V is the candidate. It is confirmed only if it is a clear trough and the later steps stay low. No numeric rule is given for "clear trough".

3. Teacher rollout. The teacher gets the task, the current skills, the student's steps before the deviation point, and the student's full failed run as "what to avoid". It continues from step t*, max 10 steps. After each teacher step an "inline reflector" writes a short hint for the next step. The hint is not saved in the teacher trace. The continuation is kept only if it passes the task evaluator. If it fails it is retried up to 3 times, then dropped.

4. Paired suffix contrast and skill generation. For each kept case a summarizer writes: the student's mistake, the teacher's fix, what the skill was missing, a general direction. A generator then reads all the case analyses and picks one of three actions: improve_skill, optimize_description, or skip (when evidence is thin).

5. Regression-gated update. An LLM editor applies the edit to produce a new skill s'. An LLM reviewer reads the old skill s and s' and gives two scores in [0,1]: "no regression" (no useful rule deleted or weakened) and "generalizable rule" (not a one-off patch). The edit is accepted only if both are at least 0.5 (Eq. 9).

Is the skill validated by re-running the student? No. The gate is an LLM reading two texts. The Student Rollout section says the success pool "is later used to test whether a candidate skill update damages previously working behavior", but the gate section describes no such test. The only check by execution is the evaluation in the next round.

How many teacher calls? Per failed run: up to 3 attempts x up to 10 steps, each step followed by a reflector call. Then one summarizer call per kept case, plus generator, editor and reviewer calls per skill. No totals are reported.

Labels: needed. The evaluator, the Prog signal and the teacher acceptance test all use ground truth.

## Setting, benchmarks, models

- Student: Qwen3-32B. Teacher and all other modules (summarizer, generator, editor, reviewer): Qwen3.5-397B-A17B. Temperature 0.7. Max 8,096 tokens per call (12,000 for the evolution modules).
- ToolQA: SRA-Bench skill corpus. Test set split into six disjoint groups of 238 examples (1,428 total). Row "SkillPivot-g i" is the corpus after evolving on groups g0 to g i in order. Every row is tested on all six groups.
- LogicBench: SRA-Bench skill corpus, six even groups (sizes not given). Each "Evo g i" evolves on group g i and is tested on all six.
- WildClawBench: all tasks that provide and invoke skills (count not given). Each "Evo g i" is one more round of evolution over the complete task set, then evaluation on that same set.
- Cross-model test (RQ3): GPT-4o mini, Gemini 3.1 Flash-Lite, DeepSeek-V4-Pro, Qwen3.5-397B-A17B, Qwen3-32B.
- Baselines: SkillClaw, SkillForge, AutoSkill.
- All configurations run three times.

## Metric

- Task success rate (accuracy) in percent, by each benchmark's official protocol. Mean and standard deviation over 3 runs.
- Table 2 adds: Point Agree. (majority vote of three LLM judges, DeepSeek-V4-Pro, Qwen3.5-397B and Claude Opus 4.6, that the chosen step is a reasonable turning point), Cont. Success (share of teacher continuations that pass), Avg. Steps of the continuation, Invalid Calls rate.
- Figure 3a adds modified skill length in characters.

## Results, including weak and negative ones

- ToolQA (Table 1). Non-evo mean 53.18 +/- 0.32. After g0: 54.72. g1: 55.32. g2: 57.33. g3: 57.38. g4: 58.05. g5: 59.36 +/- 0.20. Total gain 6.18 points.
- The first round is small. After evolving on g0 only, g0 itself goes from 52.59 to 56.08 (+3.49). The five unseen groups gain +0.15 to +2.66, about +1.15 on average (my arithmetic from Table 1).
- Not monotonic. Column g4 falls from 58.43 (after g2) to 54.49 (after g3). Column g5 falls from 58.85 (after g2) to 54.78 (after g4).
- No clean held-out set in the headline. The g5 corpus has seen failures from all six groups and is tested on the same six groups.
- Against other methods on ToolQA (Figure 3a). Non-evo 53.18. SkillClaw 54.85 (1,788 characters changed). SkillForge 53.95 (1,240). AutoSkill 53.85 (8,965). SkillPivot 59.36 (1,338). Longer edits did not help.
- Evidence form (Figure 3b). Whole-trajectory reflection 52.52, which is below the 53.18 baseline. Failure-only reflection 56.30. Teacher-only imitation 55.46. Paired suffix contrast 59.36. No error bars.
- Other models (Figure 4a). All five models gain with the evolved skills on all six groups. Values read off the plot: Qwen3-32B about 51 to 55 before and 58 to 60 after. GPT-4o mini about 50 to 52.5 before and 55 to 58 after. DeepSeek-V4-Pro about 53 to 58 before and 56 to 60.5 after. Qwen3.5-397B about 55.5 to 60 before and 62 to 63.5 after. Gemini 3.1 Flash-Lite about 57 to 61 before and 61.5 to 63.5 after. The small student with evolved skills (about 60) matches or beats the big teacher with the original skills (about 58).
- The text says the "one-round evolved corpus" is used here. The Qwen3-32B line matches the SkillPivot-g5 row of Table 1, not the g0 row. So "one round" seems to mean one pass over all six groups.
- Where to intervene (Table 2, ToolQA failures). Teacher from scratch: 35.65% success, 6.57 steps. Random step: 38.06%, 10.98 steps, 29.68% invalid calls, 13.32% judge agreement. Direct LLM locator: 45.28%. Step-wise LLM verifier: 49.55% (72.18% agreement, the highest). SkillPivot detector with the big teacher: 56.18%, 5.95 steps, 2.93% invalid calls, 70.81% agreement. SkillPivot detector with the student as its own teacher: 37.40%, 11.71 steps.
- So even in the best case the teacher fails to repair about 44% of the student's failures. Those cases produce no skill evidence.
- The teacher is not much stronger than the student here. From scratch it solves only 35.65% of the tasks the student failed.
- Review gate (Figure 4b). Heatmap of no-review minus review accuracy, 6 source groups x 6 evaluation groups. Values range from -2.94 to +3.36. 17 cells are positive (no review is better), 13 negative, 6 zero. The mean of the 36 cells is about +0.32 points in favor of no review (my arithmetic). Most values are multiples of 0.42, which is one example out of 238, so each cell is a difference of a handful of examples. No error bars. The authors say review is for long-term stability, not short-term accuracy. The figure does not show that.
- LogicBench (Table 3). Non-evo 86.54 +/- 1.05. SkillPivot 88.01, 88.80, 88.01, 89.20, 90.83, 91.22 across source groups. SkillClaw 87.14 to 88.15. SkillForge 87.19 to 89.50. AutoSkill 86.30, 87.27, 85.91, 85.52, 82.00, 85.55. AutoSkill is below the no-evolution baseline in five of six settings. Standard deviations are 0.3 to 2.4, so many gaps between methods are inside the noise.
- WildClawBench (Table 4). Non-evo 34.35 +/- 0.68. SkillPivot by round: 36.36, 52.81, 57.93, 64.58, 70.40, 73.00. SkillClaw ends at 65.27, SkillForge at 60.73, AutoSkill at 63.45. SkillForge after round 1 is 32.17, below baseline. This benchmark is evolved and tested on the same tasks, round after round.

## Limitations

Authors': none stated. There is no limitations section.

Mine:
- Needs ground-truth answers at three places (evaluator, Prog signal, teacher acceptance). Not usable as written on unlabeled tasks.
- The "regression gate" does not run anything. It is an LLM comparing two texts with a 0.5 threshold. The review ablation does not show it helps.
- No cost reporting at all. No tokens, dollars, calls or time. The teacher loop is heavy (up to 30 steps plus 30 reflector calls per failure).
- Gains on ToolQA are modest in absolute terms (+6.18 points) and the per-round gain is close to the group-to-group noise.
- Headline ToolQA and WildClawBench numbers mix repair of seen tasks with transfer.
- The weights 0.4, 0.3, 0.3 and the trough rule are not ablated. The paper title for RQ4 says the signals are "meaningful" but no signal is removed.
- The inline reflector is not ablated.
- The teacher is only modestly stronger than the student on ToolQA.
- Group sizes for LogicBench and task count for WildClawBench are missing.
- Figure 3b and Figure 4b have no error bars.
- It only edits an existing good skill corpus. Nothing on writing a note from nothing.
- No per-task analysis of which tasks were fixed or broken.

## Assumptions not tested

- That text edits are the right fix. No executable artifact is compared.
- That failures are "localized" in general. This is the paper's first contribution, but there is no count of how many failed runs had a confirmed deviation point.
- That continuing from the student's prefix beats restarting for the quality of the final skill. Table 2 shows it helps the teacher succeed (56% vs 36%). The downstream skill built from from-scratch teacher runs is not tested, except loosely as "teacher-only imitation" in Figure 3b.
- That the LLM gate prevents long-run decay.
- That the method works when the gold answer is not available for the Prog signal.

## C1 to C6 mapping

- C1 (forms of knowledge, text vs program): not covered. All updates are text edits to skills. RQ5 and Figure 3b compare kinds of evidence (whole run, failure only, teacher only, paired suffix), not kinds of artifact.
- C2 (student strength): partly. RQ3 and Figure 4a run the same evolved skills on five models of different strength and all gain. Table 2 varies teacher strength (self-teacher 37.40% vs big teacher 56.18%). No threshold, no case where text was not enough for a weak model.
- C3 (predict before paying): partly, and only in a narrow sense. Trace features (execution validity, progress toward the gold answer, action repetition) locate where the run went wrong (Eq. 6 to 8, Table 2). They are not used to predict whether a remedy will work. The generator's "skip" action is a weak pre-decision with no reported accuracy. Nothing on the teacher's diagnosis as a predictor and nothing on the student's self-forecast.
- C4 (economics): not covered. Raw ingredients only: 56.18% continuation success (so about 44% failed builds per attempt set), 5.95 average continuation steps, up to 3 retries (Table 2, Experimental Setup). No unit of cost, no break-even.
- C5 (online per-task choice): not covered. One path: always evolve the skill.
- C6 (harm): partly, at the aggregate level. Whole-trajectory reflection falls below baseline (52.52 vs 53.18, Figure 3b). AutoSkill falls below baseline on LogicBench in five of six settings, down to 82.00 vs 86.54 (Table 3). SkillForge falls below baseline in WildClawBench round 1 (Table 4). SkillPivot itself loses 3.9 points on group g4 between rounds g2 and g3 (Table 1). The gate is built for harm but is not shown to reduce it (Figure 4b). No per-task harm count.

## What this means for Loopy

What we can no longer claim:
- That building a text note "from the step where the small model went wrong" is new. This paper is exactly that: find the deviation step, have the strong model continue from it, write the note from the contrast.
- That paired contrast beats failure-only or teacher-only evidence. Published here (Figure 3b) and in D-Skill (2610.28914, Table 2).
- That a text skill written with one model's help also helps other models. Published (Figure 4a).
- That a small model with a better text skill can match a bigger model without it. Published (Figure 4a, text of RQ3).
- That automatic skill edits can make an agent worse. Published at the aggregate level (Figure 3b, Table 3).

What stays open:
- Text vs program for the same failure (C1). Not here.
- Predicting which remedy will work before paying (C3). Not here. Their detector locates, it does not predict, and it needs the gold answer.
- Any economics (C4). Nothing here.
- A per-task choice among rent, coach and compile (C5). Not here.
- Per-task harm (C6). Not here.
- Whether a note still fails when the failure is labeled procedural. Not examined.

How it relates to our pilot:
- Their repeated-task result is the nearest thing to our setting. On WildClawBench, text skills evolved and tested on the same tasks go from 34.35% to 73.00% over six rounds, but round 1 gives only +2.0 points (Table 4). On ToolQA the first round fixes few of the tasks it was built from: +3.49 points on g0 is about 8 net tasks out of about 113 failures (my arithmetic from Table 1). So a single round of text coaching repairing few failures, as in our coach 1 of 6, is in line with what they report. Their gains come from accumulating rounds.
- Their teacher fails to repair about 44% of failures even from the right step (Table 2). We should count failed builds the same way. They never price them.

Design lessons to copy for COACH:
1. Have the cloud model continue from the small model's own prefix, not restart. Continuation success 56.18% vs 35.65% from scratch, with fewer steps (Table 2).
2. Show the cloud model the student's failed ending as "what to avoid".
3. Keep the edit small and conditional. 1,338 characters beat 8,965 (Figure 3a).
4. Do not reflect on the whole failed run. It made things worse (Figure 3b).
5. Write recovery procedures, not general advice: retry with another date format, relax an over-specific filter, reformulate the query, verify the candidate (RQ2 text).
6. Let the writer say "skip" when the evidence is thin, and record how often it does.
7. Accept the teacher's fix only if it passes the evaluator. They do this. We already do.
8. Do what they do not: accept a note only after re-running the student. Their gate is an LLM text review and their own ablation does not support it.
9. A cheap locator to test: lowest step score from tool validity plus action repetition. Drop their Prog term, since it needs the gold answer.
