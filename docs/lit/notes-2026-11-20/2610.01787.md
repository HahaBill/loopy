# 2610.01787 · Not All Experience Belongs in the Weights: Component Routing for Self-Improving GUI Agents

Wu, Ding, Huang (South Dakota State University). arXiv v1, 1 Oct 2026. 46 pages. Code and data "will be released" (not out at time of reading).
Source read: arXiv HTML full text (6870 lines) plus the PDF for every figure and table.

## Claim (one paragraph)

A trajectory is the wrong unit of experience. Split a GUI agent's own experience pool into four components (locators, procedures, state facts, lessons). Send each one either to the prompt ("context", retrieved notes) or to the weights (LoRA fine-tune), using the same items in both arms. The winner differs by component. Key number: route gain Δ = success(weights) minus success(context), MobileGym, pooled over three backbones: locators +4.9, lessons +1.5, procedures -4.2, state facts -4.1 points (Sec 4.1, Fig 4, Table D.2). A linear rule in two pool statistics, recurrence r and state-conditionality κ0, recovers the winning side in 24 of 24 held-out cells (Sec 5.1, Table D.1, D.2). Routing by the rule beats the better single destination by +3.5 points on average over 3 backbones and 2 environments (Table 2).

## Method, in enough detail to reproduce

**Pool.** The base agent runs every training template many times and keeps all trajectories, failed or not. MobileGym: 122 templates x 20 episodes at temperature 1, per seed (2440 episodes, booked at 3.7 GPU-hours). AndroidWorld: each pool task 10 times. Each step stores screenshot, app state, element list, action, target (App B.1).

**Four components** (Sec 3, App A.1). A rule-based extractor (the "lenient" one, names normalized) emits items. Each item has a key, a payload, a state condition, a one-line note form, and a training-sample form.
- Locator (G): where a named element is. Key (app, role, element name). Payload: coordinates.
- Procedure (P): a run of three consecutive action targets inside a task family. Key: the three targets. Note: "after A and B, the next step is usually C".
- State fact (F): a precondition that must hold before an action works. Built from one failed and one successful attempt at the same target. Key (app, target, predicate).
- Lesson (L): an action that failed in a state, paired with the action that later worked there. Key (app, state, failed target). Trained as a preference pair.

**State signature.** Set of path-value pairs of the app state, volatile fields removed (MobileGym). On AndroidWorld: set of visible accessibility nodes, capped at 500. Two steps match "exact" if Jaccard ≥ 0.9, "relaxed" if 0.5 ≤ J < 0.9.

**Context route.** Library indexed by app and key. At each step rank same-app items by Jaccard between the item's source state and the current state. Exact matches first, relaxed fill, top five notes appended to the prompt. Procedures retrieve in two stages (skill file of the most similar task text, then step items). Rest of prompt unchanged.

**Weights route.** LoRA rank 16, α 32, 3 epochs, lr 1e-5, vision tower frozen, merged before serving, base prompt with no notes. Supervised fine-tuning for G, P, F. DPO for lessons. Every adapter reaches ≥ 0.90 token accuracy on a held-in tenth (Table C.1).

**Both.** A coexistence arm serves the tuned model plus the notes.

**Aggregate arms.** all_C (four libraries, max 2 notes per component, 8 total). all_W (one adapter on G+P+F, then DPO on L). routed (each component where the held-out rule says: G and L to weights, P and F to context). anti_routed (reverse).

**Whole-trajectory baselines.** Self-retry with three samples. Success-filtered fine-tuning on whole trajectories. Retrieve one similar trajectory. Retrieve ten step records by task text. Context-then-distill.

**Controls.** Random notes from other apps. Notes with shuffled keys. Training samples with shuffled labels.

**The rule** (Sec 5.1, App D). Score s(c) = α·r(c) - β·κ0(c) - γ. Positive means weights. Weighted logistic loss on the sign of Δ(c), ridge on standardized inputs (λ = 1/number of cells), cells whose interval crosses zero get weight 0.5. Gradient descent from zero, step 0.1, 20 000 iterations. Fit on 16 cells, test on the 8 cells of the held-out backbone family. Full fit: (α, β, γ) = (11.29, 5.73, 1.28). Folds: α 9.01 to 9.32, β 4.86 to 5.28, γ 0.70 to 0.94. Algorithm 1 gives the whole routine.

## The two properties, exactly (answer to the specific question)

Both come from the pool alone, before any route is trained (Sec 3, Eq 2 to 4).

1. **Recurrence r(d).** For each episode p that produced item d, take the other pool episodes on the same app but a different task template. r is the share of those episodes whose extracted keys contain d's key. Average over the episodes that produced d. Component value = mean over items. In words: how often the same key comes back in unrelated tasks. Values (MobileGym, Table A.1): locators 0.39, procedures 0.05, state facts 0.32, lessons 0.45.

2. **State-conditionality κ0(d).** Take all pairs of occurrences of d's key. Split them into pairs whose states match exactly and pairs whose states match only loosely. a_E and a_R are the shares of pairs in each tier whose payload agrees (position within 0.5 percent of the screen diagonal, or the same next target). κ0 = 1 - a_R / a_E. Component value = median over items that have pairs at both tiers. In words: how much the payload stops being right when the state is only roughly the same. Values: locators 0.10, procedures 0.66, state facts 0.56, lessons 0.53. Only a minority of items have a κ0 at all ("valued" share: 21% of locators, 6% of procedures, 53% of state facts, 15% of lessons, Table A.1).

There is also an online check, κ(c) (Eq 4): the share of the context gain that is lost when retrieval is relaxed-only instead of exact-only. It needs the context route to have run. Rank agreement with κ0 is only Spearman 0.56 over 12 cells (Sec 5.1).

**Can the rule be reused to pick a text note versus an executable function?** Not as fitted. My reading:
- The two features can be computed for Loopy. Recurrence: how many other AppWorld task templates need the same API step or call sequence. State-conditionality: how much the right call sequence changes with database state or task parameters.
- The sign and coefficients cannot be carried over. In this paper both destinations are consumed by the same model's policy. A compiled function takes the student out of the execution loop. That changes what κ means. Weights lose the "when" (Fig 2, App G.1). Code can hold the "when" as explicit branches.
- Recurrence does map onto our economics axis (C4). In the paper recurrence reaches the weights as "number of updates a key receives" (Sec 5.2). For Loopy it would be "number of reuses that amortize the build".
- The rule needs labels. Fitting it required route gains for both arms on two other backbones. "Before any training" holds for the features, not for the rule.
- So: reuse the design (measure item properties first, fit a sign rule, test on a held-out student). Refit on coach versus compile outcomes.

## Setting, benchmarks, models

- MobileGym: simulated phone, 20 apps, 416 templates (160 train, 256 test). 5 apps held out by a fixed rank rule. Held-out tiers: 165 new templates on seen apps, 59 templates on unseen apps. 1106 paired instances per seed. State checker, no model judge.
- AndroidWorld: 116 tasks, 20 apps, 8 held out. 58 held-out tasks x 4 instances = 232 per seed.
- OpenApps (version change study): 15 tasks, 6 apps, 2 versions, 150 instances per seed.
- Models: GUI-Owl-1.5-8B, ScaleCUA-7B, Qwen3-VL-8B. Producer and consumer are the same model in the main study. Ladder for the producer-consumer study: Qwen3-VL 4B, 8B, 32B and GUI-Owl 8B, 32B.
- Three seeds. Greedy decoding at evaluation. Analysis said to be fixed before the runs.

## Metric

Held-out success = share of held-out instances the environment's deterministic checker accepts. All gains are paired differences on the same (template, instance, seed). Intervals are paired bootstrap, 10 000 resamples, 95 percent. Route gain Δ(c) = U(W_c) - U(C_c) (Eq 1).

## Results, including weak and negative ones

- Base agent success is low: 16.7 to 24.0 percent (Table 2). Routed reaches 30.5 to 34.8.
- Both routes help every component over the base. Context +1.8 to +5.2, weights +0.8 to +6.7 (Fig 4c). What differs is which helps more.
- Lessons lean to weights weakly. The interval includes zero in 3 of 6 lesson cells (Table D.2). 5 of 24 cells overall cross zero.
- Routed versus better single destination: +4.4 on MobileGym (all three backbones). On AndroidWorld +5.0 (Qwen), +3.2 (ScaleCUA), and -0.3 [-2.6, +2.0] for GUI-Owl, so it only matches there (Table E.2).
- Reverse assignment loses 8.9 (MobileGym) and 6.7 (AndroidWorld) against routed, but still beats the base agent.
- Whole-trajectory methods are weak. Fine-tuning on whole successful trajectories gains +0.7. Retrieving one similar trajectory is below the base on all three MobileGym backbones (21.0 vs 21.6, 15.1 vs 16.7, 18.1 vs 19.2). The best whole-trajectory baseline is self-retry with three attempts (+4.8 over base on GUI-Owl).
- Interventions (Table 1, E.1). Copying procedure items 8x before fine-tuning lifts the weights route by +3.5, moving Δ from -4.2 to -0.8. It crosses zero only on Qwen (+1.0). So the intervention moves toward the boundary but does not flip the sign on average. Dose response on GUI-Owl: x1 +0.3, x2 +1.2, x4 +1.8, x8 +3.3. Ten times the learning rate adds only +1.0. Retrieving notes by task text only (no state match) costs 3.9 (procedures) and 3.4 (state facts). Reading the state from screen elements instead of the hidden app state costs 0.7.
- Controls. Random notes from other apps: -1.5 to -1.7. Shuffled keys: worst of eight arms -1.1.
- Readout probe (Sec 4.3, Table E.4). Before training a note changes the action on 42 percent of probed steps (33 procedures to 48 lessons). After the same items are in the weights: 16 locators, 15 lessons, 22 procedures. After/before ratio falls with recurrence, Spearman -0.92 (12 points).
- Conflict (Sec 5.3). Weights trained on app version 1, notes from version 2. Stale weights alone: -8.4. Fresh notes alone: +3.3. Both together: 2.7 to 12.7 points below notes alone. At the divergence step (520 steps) the agent follows the note 52 percent (low recurrence) vs 43 (high), the weights 34 vs 21, neither 14 vs 36.
- Sensitivity (Table F.1, GUI-Owl, seed 0 only). Thresholds, note count, LoRA rank, library cap move things by under 1 point. Pool of 5 episodes per template instead of 20 costs up to 2.0.

## Producer and consumer gaps (answer to the specific question)

Sec 4.2, Sec 6, Fig 5, Fig 9, Table E.3. Procedures only. Every adapter gets the same sample count (5600, or 1900 for 32B consumers).

- **Notes travel.** Notes help every consumer whoever wrote them. A stronger producer helps more. Qwen 8B consumer: +2.2 from 4B notes, +3.6 from its own, +4.8 from 32B notes. The 32B consumer still gains +3.2 from 8B notes.
- **A weaker consumer gets less out of the same notes.** From 32B notes: 4B consumer +3.1, 8B +4.8, 32B +5.5 (Table E.3). The authors do not stress this. It matters for us.
- **Weights do not travel.** Fine-tuning the 8B on another model's procedures: -2.3 (4B), -1.4 (32B), -7.5 (other family, GUI-Owl). Its own: +0.9.
- **Most of the weights gain is practice.** Training on the consumer's own successes on families it already solves gives +0.6 versus +0.9 with everything. Within 1.1 points on all five consumers.
- **Three gaps, measured before transfer** (Eq 6). Information gap g_I = producer pass rate on a task family x consumer fail rate on it. Policy gap g_P = share of shared states where the two models act differently. Producer ability g_A = producer's base success.
- Context gain rises with the information gap: +0.2 in the lowest sixth of cells to +11.3 in the highest. Spearman 0.65 over 720 cells (15 pairs x 16 families x seeds). Producer ability alone: 0.20, and 0.05 once the information gap is fixed.
- Weights gain falls with the policy gap: +4.0 to -5.7, Spearman -0.52.
- A foreign producer is a policy gap (0.46), not an information gap (0.07). Retraining the foreign producer on the consumer's successes closes the policy gap to 0.17 and brings its weights result back to -2.0.
- Upgrade: a note library carries over to a new consumer. Adapters must be rebuilt.
- Their line: "A note pays when it says something the consumer does not know, whoever wrote it." (Sec 6.1)

## Limitations

**Authors'.** There is no limitations section. Caveats are scattered: lessons are weak (interval includes zero in half the cells). AndroidWorld intervals are wide and routing only matches all-context on GUI-Owl. The 8x dose does not cross the boundary on average. Sensitivity is one seed on one backbone.

**Mine.**
- The rule is fitted on four points. The 24 cells are four components replicated over three backbones and two environments, with almost the same coordinates each time. A line with three free parameters that separates two clusters from two clusters is close to guaranteed. "24 of 24" shows the pattern is stable across backbones. It does not show the rule generalizes to a new kind of knowledge.
- The stronger test is the twelve halves (Table D.4). But it varies recurrence only. The role of κ rests on the "remove the state condition" intervention, which changes retrieval, not the measured κ0.
- κ0 exists for only 6 percent of procedure items and 15 percent of lesson items.
- Fitting the rule needs both routes already run on other models. The prediction is cheap only for the second model onward.
- Effects are a few points on a 17 to 24 percent base, three seeds.
- No break-even. Notes cost 7 percent more prompt tokens on every episode forever. Adapters cost GPU-hours once. The paper reports both and never compares them over a horizon.
- Table H.1 lists self-retry (three attempts) and the two retrieval baselines at a token ratio of 1.00. That cannot be the full cost of three attempts or of a pasted trajectory. Treat the token column as partial.
- MobileGym keys use the hidden app state. The screen-only variant costs 0.7 points, so this is minor.
- GUI agents, vision-language models, Chinese prompts. No API or code tasks.
- The related-work section cites a long block of the authors' own unrelated papers (federated learning, UAVs). Not a result problem, but a care signal.
- Code not released yet.

## Assumptions not tested

- The four-way split is the right split, and extraction rules are accurate.
- The boundary is linear, and it holds for components outside these four.
- One LoRA recipe stands for "weights". (Rank and learning rate were probed lightly.)
- Five notes per step stands for "context".
- The only two destinations are prompt and weights. No executable artifact. No option to hand the task to a stronger model.
- The student executes in both arms. Nothing tests a student too weak to act on a correct note.
- Pool statistics stay valid as the app changes (partly probed by the version study).

## Mapping to C1 to C6

- **C1 forms of transferred knowledge: partly.** Context versus weights, same items, paired (Sec 4.1, Fig 4, Table D.2). Mostly self-experience (teacher = student). Teacher ≠ student only for procedures (Sec 6). No executable program.
- **C2 student strength: partly.** Consumer ladder 4B, 8B, 32B for procedures (Fig 5a, Table E.3). Weaker consumers gain less from the same notes. No threshold where notes stop being enough, and no alternative remedy for the weak student.
- **C3 predict before paying: covered, for context vs weights.** Rule in r and κ0 (Sec 5.1). Information gap and policy gap measured before transfer (Sec 6.1, Fig 9). No teacher diagnosis, no self-forecast.
- **C4 economics: partly.** GPU-hours and prompt tokens (App H, Table H.1). No break-even, no failed builds, no dollars, no repeat horizon.
- **C5 online per-task choice: not.** Routing is per component, offline, fixed before training. No rent option.
- **C6 harm: covered.** Random notes -1.6. Cross-model fine-tuning down to -7.5. Stale weights -8.4, and stale weights plus fresh notes worse than notes alone. Retrieving one whole trajectory below base. (Sec 4.2, 5.2, 5.3, Table 2.)

## What this means for Loopy

**We can no longer claim:**
- That we are first to say the destination of experience should depend on properties of the knowledge item. Done here for prompt versus weights.
- That we are first with a predict-before-paying rule built from measurable properties. Done here, with the caveats above.
- That notes from a stronger model help a weaker one, or that the value of a note depends on what the student does not already know. Both are in Sec 4.2 and 6.1.
- That text advice can hurt. Shown with placebo notes.

**Still open after this paper:**
- An executable program as a destination. Nothing here is compiled. The student always executes.
- A student too weak to use a correct note. Their notes are the winning route for procedures and still add only about 5 points.
- Rent as an option, and cost over repeats with a break-even.
- A choice made per task, online.
- A teacher's diagnosis or a student's self-forecast as the predictor.
- API tasks with text models (AppWorld).

**Fit with our pilot.** The paper says procedures belong in notes rather than weights. Our pilot says notes mostly fail on "procedural" failures (coach 1/6) and a function works (compile 5/6). These do not conflict. Their comparison is notes versus weights, not notes versus code, and even their winning notes leave most tasks failing. Their information-gap result gives a reading of our pilot: a note pays only when the student lacks knowledge. If our small model's problem is execution, not knowledge, the information gap is small and a note should not help. That is a testable prediction, and it is ours to test.

**Design lessons to copy:**
1. Feed the same experience into every arm. Compare paired, on the same task instances, with a paired bootstrap.
2. Measure item properties before building anything. For us: recurrence (how many task templates reuse the step) and information gap per task family (cloud pass rate x small fail rate).
3. Add a readout probe. Replay the failing step with and without the coach note. Did the action change? This separates "note ignored" from "note followed, still failed".
4. Add placebo arms: a random note from another app, a shuffled note.
5. Test the rule with an intervention that changes one property (they copied items, and removed the state condition).
6. Write the assignment to disk before building. Fix the analysis before the runs.
7. Hold out a student model when fitting any rule, and say plainly how many independent points the rule was fitted on.
8. Vary student size. Their Table E.3 already hints that weaker students get less from the same note.
