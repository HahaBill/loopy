# Loopy, what to run next: literature sprint after the stage 1 result (Nov 24, 2026)

Question asked: given the stage 1 result, what is the next experiment with the best chance of a result nobody has?
Earlier sprints: `novelty-lit-sprint.md` (Oct 26, 14 papers) and `notes-2026-11-20/` (14 papers). This one adds 13 papers
(`notes-2026-11-24/`), 25 search phrasings and 5 citation trails. Stage 1 numbers come from
`results/pilot/stage1/analysis_stage1_2026-11-23.json`. Everything marked "post hoc" was computed after seeing the
result and is exploratory.

## Verdict

**Partly done by others, and the open part is the part we are closest to.**

1. The half of the thesis that stage 1 could not confirm, "advice depends on the student", is already published several
   times for text (2610.33024, 2611.18624, 2611.13144, 2605.30723, 2607.28048). It is not ours to claim.
2. "A teacher-made program lifts a weak student" is also published (LATM 2305.17126, AgentDistill 2506.14728, PLVR
   2610.19148).
3. "A program can lose to prose once the model is strong" has been **seen once, in an appendix, and never tested**:
   Huang et al., 2608.11338, Appendix G.2. A related pattern, structure helps the weakest model and hurts stronger ones,
   is in 2609.40303 for harness design.
4. **Open in what we searched:** a designed test where the same failure, the same teacher and the same student get a note
   and a function, across students ordered by their own no-help score, with a generic-note control and task-level counts
   of what each form fixes and breaks. Stage 1 is that test for weak students. No paper we read has it.
5. **Why it happens is half known.** That agents take a tool's output without checking it is published for generic tools
   (2609.05587: corrupted search, sub-agent and code returns are adopted 68%, 40% and 36% of the time; 2606.14476,
   abstract only; 2609.01852 for memory notes). **Open in what we searched:** that this is what a teacher-built function
   does to a student, and that it explains who is helped and who is hurt. No skill or program paper we read reports what
   the student does with the function. Our logs do, and they point to a simple model (below): a function substitutes for
   the student, a note amplifies the student.

Confidence: medium. Not searched: paywalled venues, patents, non-English work, company blogs. The papers closest to us are
weeks old, so the "papers citing X" trails came back empty (0 or 1 citing papers each) and we relied on Semantic Scholar
recommendations and reference lists. Two leads were read only as abstracts (list at the end).

## The move

**Recommended: a small stage 2 that turns the stage 1 pattern into a tested claim. Working title: "Substitute or
amplify".** When this was written nothing below had been run. **Update, Nov 24, 2:50 AM:** Alfredo approved the next
step. Part B was written into `experiments/stage2/PROTOCOL.md` before any run and started for the three lower-tier
students (138 runs, estimated $4 to $5). The two upper-tier students and part A have not been run.

The claim to test: a function replaces the student's ability with the function's own reliability, the same for every
student. A note multiplies what the student can already do. So the better form flips with the student's own pass rate,
and a function can hurt a student that would have passed alone.

Stage 2, in two parts, on the same 30 scenarios, the same teacher runs and the same 23 functions (no new function builds):

- **Part A, fill the ability axis.** Stage 1 has three students at 3% to 20% alone and two at 87% to 90%, nothing between.
  Screen four candidate students on the 30 version 1 tasks alone, keep two or three by a rule fixed before screening
  (closest to 40%, 55% and 70%), and run them through the unchanged stage 1 pipeline (alone, checked note, function,
  generic note). Candidates on the provider today: Qwen3-235B, Nemotron-3-Super-120B, MiniMax-M3, Inkling-2-Small. The
  Nemotron family is what PLVR used, which gives a direct comparison.
- **Part B, the missing cell: the same code, handed over as text.** Stage 1 compares prose that the student reads with
  code that the student calls. Those differ in two ways at once: what is said (prose or working code) and how it arrives
  (text to weigh, or a loaded function whose return is taken as done). One new arm separates them: the teacher's function
  is shown inside a note as text, not loaded. No new teacher calls are needed. If weak students do as well with it as with
  the loaded function, the lesson is "write the advice as code". If they do no better than with the prose note, the
  lesson is "delegate the doing". A reviewer will ask for this cell; no paper we read has it.
- **Optional, if money remains:** the loaded function plus one line telling the student to check the result before
  finishing.

Predictions to write down before any run (confirmatory on the new students, since the first five were used to find them):

| | Prediction | Stage 1 hint (post hoc) |
|---|---|---|
| P1 | Function fix rate on built functions does not depend on the student | 80%, 73%, 88% on the three weak students |
| P2 | Note fix rate rises with the student's own pass rate | 4%, 26%, 55% (weak), 5 of 5 (strong) |
| P3 | Among students at 50% or more alone, the note matches or beats the function on failed tasks, and the function breaks some passed tasks | note 5 of 5, function 3 of 5; function broke 7 of 86 |
| P4 | Every student mostly calls the function once and stops; given that, the pass rate is the same for every student | 143 of 157 call-and-stop runs passed (91%) |
| P5 | Note fix rate falls as the teacher's own run gets longer; the function's does not | note 50% then 17%, function 78% then 69% |
| P6 | Code shown as text lands between the prose note and the loaded function for weak students, and breaks fewer passed tasks on strong students than the loaded function | not tested; 2609.05587 Table 3 found the same content trusted 40.2% as a tool return and 1.8% as text |
| P7 (optional arm) | The "check the result" line cuts broken tasks on strong students by half or more without lowering the weak tier's function rate by more than 5 points | not tested |

P6 is written as a two-sided question on purpose: either outcome is a result. A warning on P7 from the literature: in
2609.05587 a "verify" prompt cut adoption of bad tool output by only 4 to 10 points (Table 5). The cheaper fix for harm is
a gate, shown post hoc in the policy table below: hand over the function only where the student failed the first version
of the task.

What kills it: the function's pass rate given call-and-stop differs by student (then it is not substitution); the note
rate does not rise among mid students (then there is no flip).

Cost, from stage 1 run costs: screening about $2 to $3, each new student about $3 to $7, part B about $3 to $5 for the
five current students. With two new students that is about $13 to $19. The ledger stands at $43.54 of the $50 cap, so
this needs the cap raised to about $62 and leaves little margin. If only one part fits,
run part B first: it is the cheapest, it needs no new student, and it answers the question a reviewer asks first. About
half a day of unattended running. Both are Alfredo's calls: the spend and the protocol addition.

**Second, free, do regardless:** put the post hoc tables below into the Dec 7 demo and the Dec 15 report as exploratory
analysis, and reword the thesis. "Advice has a ceiling that depends on the student" is other people's finding.
"A function substitutes, a note amplifies" is the open one.

**Third, only if budget remains:** give the note a fairer chance (two repair rounds, as Skill Transfer 2611.18624 does),
on one weak student. Without it a reviewer can say the function only beat a one-shot note.

Not recommended:
- The rent, coach or compile picker from the October plan. For weak students the function nearly dominates (the note alone
  fixed 9 of 126 tasks the function missed), so a picker has nothing to pick until the flip at higher ability is shown.
  The rent-or-buy framing itself belongs to PACE (2610.02932).
- Harder tasks for the two strong students. It needs new teacher runs and new function builds, and the strong students
  are the expensive ones ($4 and $11 each in stage 1).

## What stage 1 already shows beyond the preset analysis (post hoc, exploratory)

All counts come from the latest run per task in `results/pilot/stage1/runs.jsonl`. They reproduce the preset counts
(note 39, function 90, generic 16 of 131). Scripts: `experiments/stage1/posthoc/`.

**Overlap of the two forms, weak tier, 126 failed tasks.** Both fixed 25. Function only 62. Note only 9. Neither 30.

**Where the thing was actually built.** A note that passed its check on the task it was written from fixed 34 of 71
variants (48%): 2 of 11, 10 of 28 and 22 of 32 by student. A built function fixed 87 of 108 (81%): 33 of 41, 24 of 33
and 30 of 34.

**By AppWorld difficulty level (weak tier).**

| Level | Tasks | Note | Function |
|---|---|---|---|
| 1 | 34 | 17 (50%) | 29 (85%) |
| 2 | 41 | 12 (29%) | 22 (54%) |
| 3 | 51 | 5 (10%) | 36 (71%) |

**By the length of the teacher's own passing run on the same task (weak tier, 112 tasks the teacher passed).**

| Teacher steps | Tasks | Note | Function | Generic note |
|---|---|---|---|---|
| 5 to 7 | 1 | 1 | 1 | 0 |
| 8 to 11 | 36 | 18 (50%) | 28 (78%) | 6 (17%) |
| 12 or more | 75 | 13 (17%) | 52 (69%) | 7 (9%) |

**What students do with the function.** In 157 of 230 test runs the student took at most 2 steps: it called the function
and finished. 143 of those passed (91%). By student: gpt-oss 35 of 41, Gemma 34 of 38, MiniMax 6 of 6, DeepSeek 33 of
33, Qwen3.8 35 of 39. MiniMax is the exception in style: it kept working for 7 or more steps in 38 of 46 runs and passed
34 of them. Median steps alone against with the function, on each student's larger group of tasks (failed alone for the
weak three, passed alone for the strong two): 13 to 2, 14 to 1, 32 to 16, 12 to 2, 15 to 2.

A caution on reading this: the function arm's wrapper tells the student to call the function and then finish the task.
So calling it and stopping is what that arm asks for, not something the students chose. What the counts add is that the
outcome of doing so barely depends on the student.

**Harm.** The function broke 9 tasks a student had passed alone: Qwen3.8 6 of 41, DeepSeek 1 of 45, Gemma 1 of 5, gpt-oss
1 of 3, MiniMax 0 of 11. In four of the six Qwen3.8 cases it took 1 or 2 steps with the function where it had taken 10
to 20 alone. One trace was read: the student called the function once, got no return value, and declared the task done.
Other students passed the same task with the same function available by doing more of the work themselves.

**Simple rules, test tasks passed out of 60 per student** (`posthoc/policies.py`). "Gated" gives the function only in
scenarios where the student failed version 1 alone. A note exists only in those scenarios, so it is gated by design.

| Student | Alone | Always function | Gated function | Note | Best of the three per task | Tasks broken: always, gated |
|---|---|---|---|---|---|---|
| gpt-oss-120b | 4 | 37 | 36 | 5 | 39 | 1, 1 |
| Gemma 3 27B | 5 | 35 | 28 | 14 | 38 | 1, 1 |
| MiniMax M3.1 Flash | 12 | 43 | 42 | 34 | 49 | 0, 0 |
| DeepSeek V4.1 Flash | 54 | 54 | 55 | 55 | 55 | 1, 0 |
| Qwen3.8 27B | 52 | 51 | 54 | 56 | 59 | 6, 0 |

For the three weak students the function wins by a wide margin. For Qwen3.8 the order reverses: always handing over the
function ends one task below doing nothing, the gate removes all six broken tasks, and the note does best. The top two
rows of that reversal rest on differences of one to five tasks.

**Cost (added after review, counts failures).** A note never pays back in 55 of 65 student-scenarios where one was
attempted. A function never pays back in 30 of 75; where it does, the median is 1.73 uses. (The median for the ten notes
that do pay back is being recomputed after a second review comment; see `LOG.md`.)

Reading: for a student that passes a task alone with probability p, calling a function of reliability q and stopping
gives q whatever p is. That helps when p is low and costs when p is above q. A note leaves the student doing the work,
so its effect depends on whether the student can carry out a long procedure, which is what the step-count table shows.

## Cross-paper map

### Agreements
- **Text help grows with the reader's strength when the task is a procedure.** 2610.33024 (+31.1 against -8.8), MASA
  (negative for 4B and 8B, positive for 14B and 32B), 2611.13144 Table 7, 2611.18624 (the original skill is worse than no
  skill in 6 of 8 weak settings). Ours: 4%, 26%, 55%, then 5 of 5.
- **Executable help gains most where the student is weakest, and flattens the differences between students.** AgentDistill
  Table 2, PLVR (spread 15.0 to 1.1). Ours: 80%, 73%, 88%.
- **Added structure can cost a strong agent.** Huang et al. App. G.2, 2609.40303 Table 10, PASE's generic skill (-3.63 on
  the strongest). Ours: 7 of 86 tasks broken on the two strong students.
- **A one-shot checked note fixes about three in ten failures.** SKILL-KD (about 30% of failed training tasks, the reading
  agent's arithmetic from its Tables 5 and 7) and ours (27%).

### Contradictions, and what would resolve them
1. **Does text help weak readers?** Artifact Distillation says yes, most: Haiku +0.071 and Qwen3.5-27B +0.070 against
   Sonnet +0.020 and Opus +0.026. D-Skill says yes, 75 to 95% of the gap. 2610.33024, MASA and stage 1 say no. Likely
   resolution: what the text carries. Artifact Distillation's tips are an insight for a one-shot answer (LiveBench
   puzzles); D-Skill merges 57 to 100 trace pairs into one long document. Ours and 2610.33024 give a procedure the weak
   reader must then carry out over many steps. The step-count table above is the direct evidence: the note works half the
   time when the teacher needed 8 to 11 steps and one time in six when it needed 12 or more. So the right axis is not
   "strength" but "can this reader carry out a procedure this long".
2. **Do programs beat prose?** Huang et al.: on cost always, on success only for the weakest model. PASE: about equal on one
   model (67.83 against 66.64). PLVR: far better on one suite, "competitive" on two. Stage 1: 69% against 27% on weak
   students. Likely resolution: the gap scales with how far the reader is from doing the task alone, which is P1 to P3.

### Shared assumptions nobody tests
- **The help is used as intended.** No skill or program paper reports what the reader does with a function: call it and
  stop, or keep working. Huang et al. come closest (94% fewer model calls for Gemini on Crafter) and stop at the word
  "rigid". The over-reliance papers measure it, but for generic tools broken on purpose.
- **The help's own reliability is not separated from the reader's ability.** Suite averages mix "the function was wrong
  for this variant" with "the reader misused it".
- **Strength is one number, usually a model family.** Nobody orders readers by their own no-help score on the same tasks.
- **Harm is a net average.** Nobody counts tasks the reader passed alone and lost with the help, except ASSAY (2606.15390)
  for text.

### Mechanism chains (candidate contributions)
- **A.** PLVR Table 2 (one program, students end equal) + Huang et al. App. G.2 (programs lose on stronger actors) + our
  call-and-stop counts → untested: with a function, success equals the function's reliability q for every student, so the
  gain is q minus the student's own rate and turns negative above q. This is P1, P3, P4.
- **B.** 2610.33024 Sec. 3.1 (weak readers break rules stated in the skill) + Skill-Use 2608.04828 Fig. 6d (a half-followed
  skill is worse than none) + our step-count table → untested: a note's chance of working is the reader's chance of
  carrying out that many steps, which the teacher's own run length predicts before any money is spent. This is P2, P5.
- **C.** Chain A + 2609.05587 Table 3 (the same content is trusted 40.2% as a tool return and 1.8% as text) → untested:
  the form itself sets how much the student defers. A function's return is taken as done; a note is weighed. That would
  make "function against note" a comparison of trust as much as of content. P4 and P6 test it.
- **D.** 2609.01852 Table 7 (removing the stale item fixes every model size; a label helps only the larger ones) + our
  gate result → untested: for a student that would pass alone, withholding the function beats telling it to be careful.

### Metric drift
- "The skill helps" is a suite average in most papers, a blinded preference in MetaSkill, and a per-task paired count in
  ASSAY and here. We use paired per-task counts on tasks the student failed alone, and separately on tasks it passed.
- "Strong" is model size (MASA), model family (Huang et al.), base score on the benchmark (2609.40303) or, here, the
  student's own pass rate on version 1 of the same scenarios.
- "Program" ranges from one function per scenario (ours) to a 37-primitive pipeline with about 100 small-model calls
  (PLVR) to a self-edited library (Huang et al.).

## Gap and falsifier

**Gap:** no study gives the same failed task, from the same teacher to the same student, as a note and as a function,
across students ordered by their own no-help score, with a generic-note control, variants of the task, counts of tasks
fixed and broken, and a measure of what the student did with the help.

**What would show it is not new or does not hold:**
- A paper citing Huang et al. (2608.11338) or PLVR that runs the designed comparison. Recheck both trails in two weeks.
- SkVM (2604.03088), read only as an abstract, turning out to compare compiled and text skills across model strengths.
- In stage 2: the function's pass rate given call-and-stop differs by student; the note rate stays flat among mid
  students; the check line does not change the broken-task count.
